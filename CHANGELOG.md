# Changelog

All notable changes to Meta Brain are documented here.

## [Unreleased]

### Added

- Added owner declassification into an explicit shared zone (`owner declassify-preview`, `declassify-publish --destination-id --destination-zone`, `declassify-proposal-publish --resource-id --resource-revision --destination-id --destination-zone`): the owner previews the exact sanitized body, title, metadata and citation set beside the pinned private sources, then explicitly publishes with a typed PUBLISH confirmation. The shared copy is an ordinary revision-gated memory item with zero citations; private lineage travels only through encrypted accepted `derived_from` relations unreadable from shared-only sessions. Catalog publication stays a separate act that never opens a body, frozen grants never gain the new item, forged owner/user intent stays inert, and a moved private root marks the derivative with a generic `derivative_source_changed` warning without disclosing private identifiers or rewriting the conclusion. The owner console Inbox review surface gains a matching declassification panel on the same session and service calls.
- Added explicit bounded multi-level synthesis (`--profile synthesis` on `owner job-create`, with a selection draft passed as `--input-file`): the owner names every input (each pinned to one revision), the objective, and the requested level (`l2` or `l3+`), and the job produces pending synthesis proposals carrying `MemoryKind.Synthesis`, the owner's level, assistant authorship, reported-source evidence, and one citation per grounded input at the revision it read. A synthesis job requires at least two distinct inputs, an owner objective, and a level; an `l3+` request additionally requires a selected input that is itself an `l2`/`l3+` synthesis item. Every selected input is revalidated before the private read, before the provider send, and before the commit, so a source that moved or was revoked blocks the next step and releases the reservation; a selected input set whose pinned citation lineage revisits the same resource is refused by the same bounded lineage walk the review uses. Each item must ground in verbatim passages of the exact inputs it names (an item spanning inputs must ground in two distinct inputs), and neither the level nor the number of cited inputs upgrades evidence. `owner job-*` output now lists the pinned inputs, objective, and level, and `owner proposal-read` reports whether the sources a pending proposal cites still match (`CITATIONS state=current|needsReview reasons=... stale=...`).
- Added a computed citation review to the owner review surface: a pending proposal whose cited source moved, disappeared, became unavailable, or was revoked is served as needing review, naming the cited resource, and the same evaluation walks a cited memory item's own pinned citations with the bounded lineage policy the job scope uses, so a root that changed or was revoked underneath an unchanged cited item is served as `citedSourceLineageChanged` instead of the output reading as current; a cyclic or unbounded lineage is reported rather than read as current. The proposal's content, revision, level, and citations are never rewritten and no citation is silently re-pinned. The owner console shows this in the review pane, which serves the first cited input it can read beside the content — a registered source's exact revision text, or a cited memory item's exact body at the revision the citation pins through the same owner detail read the library uses — and reports a revision the service does not serve as a refusal instead of substituting another revision or resource, while listing every citation with its pinned revision. Stored single-source job records are migrated on read to the current input-set scope instead of becoming unreadable.
- Added research-note and trend structuring profiles to the existing bounded model-job path: research asks the model to separate source-reported claims and limitations, observations, user hypotheses, questions and explicit intention proposals; the trend prompt limits analysis to the selected source revision and asks the model not to treat repeated mentions or citations of one origin as independent confirmations. Both request source citations, grounded excerpts and explicit offset-qualified occurrence times where present; outputs remain pending owner review. These semantic instructions do not guarantee correct interpretation. URLs are not fetched and proposals are not auto-published.

- Added the coding-session structuring profile (`--profile coding-session` on `owner job-create`): structures normalized coding-session transcripts into pending proposals across problem, attempt, result, decision, and lesson kinds in the destination inbox without auto-promotion. Enforces strict attribution separation (assistant claims never override observed tool results; passing local tests never infers production deployment via `unverified_inference` fail-closed checks), preserves known project, environment, and commit/version conditions in proposal applicability while keeping unknown fields null (`applicability_ungrounded` fail-closed checks), anchors every proposition to complete verbatim excerpts with exact byte-level source spans (`SourceSpan(Start, End)` in memory source references), supports dual source reading from both registered sources and source snapshots, and ensures hostile directives inside transcripts remain inert with zero execution authority.
- Added scoped model job execution and provider egress controls (`owner job-create`, `job-start`, `job-cancel`, `job-status`, `job-list`, `job-ledger`, `provider-config`): jobs execute with immutable scope snapshots revalidated before source access, provider call, and proposal commit; enforce pre-send caps of 10,000 input tokens using a formally grounded full-request bound (tied directly to wire JSON serialization in `OpenAiCompatibleProviderAdapter.BuildRequestJson` with cited primary-source DeepSeek-V4.1-Flash 1M context, ByteLevel BPE with complete 256-byte coverage proving at most 1 token per UTF-8 byte, and official Jinja2 chat template delimiters using U+2581 separators and 30-token thinking mode framing bound at 32 tokens, denying unapproved models, tokenizers, or context limits with `unknown_context`), 2,000 output tokens, $0.25 per job, and $5.00 rolling 30-day budget with historical $0.0054 reserve; require exact provider pricing cards (unknown pricing/context denies); output boundary validates strict JSON schema and verbatim source text grounding, generating strictly inert proposals with fixed non-owner attribution and no shell, grant, or key authority; ambiguous post-send failures (abrupt connection drops after accept, non-success HTTP errors, malformed response JSON, missing usage) strictly retain budget reservations in the encrypted spend ledger while only proven-not-sent pre-send denials release reservations; actual billable tokens from completed calls are committed to the ledger with usage cap violations failing closed without erasing spend; source enrollment validation (`ValidateSourceEnrollment`) enforces fail-closed behavior across all phases: corrupt or unavailable enrollment metadata truthfully refuses job creation before private read, fails closed before send with reservation safely released, and fails closed before commit preserving ledger spend with zero proposals committed and source text preserved intact; true source revocation (`source-revoke`) between create and start fails closed and releases pre-send reservation, and mid-flight revocation before commit revalidates source availability, halting execution and aborting proposal commit while preserving source and committing billable spend; in-flight cancel, timeout, and restart recovery halt execution and retain unknown reservations in the encrypted spend ledger; credentials and spend ledger persist encrypted in the vault with secure in-process `.env` or secret input and no secret argument exposure. Live provider execution was verified under explicit affirmative owner authorization using product model `deepseek-flash` on the agreed synthetic research note, establishing real token accounting (256 in / 482 out, conservative local rate calculation $0.0006552 USD), proposal commit with inert assistant attribution, reservation release and settlement in the encrypted spend ledger, and persistent readback of the same job, proposal, and source across service restart and owner unlock.
- Added explicit owner-selected preservation and exact availability tracking for enrolled external sources (`owner source-status`, `source-relocate`, `source-snapshot-list/preserve/read/retain/purge`): status fingerprints the exact enrolled bytes rather than trusting size/mtime, reports missing/changed/unreadable without scanning or following another path, and advances registered-source availability revisions. Relocation requires an explicit owner-supplied candidate whose full bytes match the enrolled generation anchor; snapshots are opt-in encrypted canonical resources with retention and purge tombstones, and the original external file is never written, moved or deleted by product code.
- Added owner ingestion operations and safe background refresh for enrolled sources (`owner source-list`, `source-pause`, `source-resume`, `source-refresh-optin/optout`, `source-refresh` alongside the existing `source-status`/`source-ingest`/`source-relocate`/`source-revoke`): the allowlist listing reports each source with its life, checkpoint, refresh consent and actual encrypted cache scope (journal/snapshot ciphertext sizes and snapshot revision) without echoing private locators; pause stops status reads, ingest and refresh with no transcript open; an owner-opt-in background loop advances opted-in sources without a manual command while unlocked, running one idempotent incremental pass over the allowlist only for opted-in sources and skipping every other source with an explicit reason and no read; a requested lock cancels the in-flight pass at its next per-source boundary and pause/disable stop reads with no checkpoint movement; revoke stops refresh and explicit re-enrollment starts a new generation on a fresh checkpoint; lock and restart deny every private read and refresh with no plaintext queue, and unlock resumes persisted checkpoints and consent without duplicates. Diagnostics carry bounded codes only, with no transcript, locator or secret.
- Added owner research capture of verbatim unstructured text (`owner research-capture --resource-id --zone-id --input-file` with optional `--title`/`--source-url`/`--source-author`/`--source-date`, read back with `owner research-read --resource-id [--resource-revision --output-file]`): the note text is persisted encrypted as one registered source through the existing source registry before any structuring or model job could run, so capture needs no provider, never fetches or validates the URL, classifies nothing, and keeps omitted URL/author/date unknown instead of inferring them. The captured note keeps its declared origin role, reads back byte-for-byte after restart and unlock, anchors downstream citations at its live revision, and never exposes its text on the metadata source wire. While the vault is locked the capture is refused with `vault_locked` — nothing reports saved and no plaintext draft or queue is written — and the agent channel cannot reach either command.
- Added the read-only Codex session adapter (format `codex.session.jsonl` version 1) on the existing enrollment and incremental ingestion coordinator: the shipped service now interprets real Codex rollout sessions, keeping each record's declared attribution (only a `message` record declaring role `user` is stored as a user statement; tool calls stay assistant-authored, tool outputs stay tool-authored, runtime notifications and control records stay system-authored), its timestamp, the session identity, the exact consumed source span and a digest of the exact record bytes, with no message body ever copied into Meta Brain. Append, incomplete tails, re-import, restart and replacement behave as the coordinator already specified, and any record or payload shape the adapter has not observed and cannot match to the upstream definition is refused with an explicit named diagnostic at its exact offset instead of being skipped or fabricated as valid. Sessions larger than the 16 MiB per-run snapshot bound are refused explicitly rather than partly read.
- Added the read-only OMP session adapter (format `omp.session.jsonl` version 1) on the existing enrollment and incremental ingestion coordinator: the shipped service now interprets real OMP agent sessions, keeping each record's source-declared attribution (a `message` declaring role `user` is stored as a user statement only when the record itself declares attribution `user`; role `assistant` stays assistant-authored; role `toolResult` stays tool-authored; `custom_message` follows its declared `user`/`agent` attribution; title, session, custom envelopes, config changes, credential pins and compaction stay system-authored), its UTC timestamp (envelope ISO-8601, message-body epoch-millis), the session identity and cwd context, the declared id/parentId chain with the compaction `firstKeptEntryId` boundary, the exact consumed source span and a digest of the exact record bytes, with no message body ever copied into Meta Brain. Append, incomplete tails, re-import, restart and lock/unlock behave as the coordinator already specifies, and any record, role, content-part, stop-reason, attribution or version shape outside the observed schema is refused with an explicit named diagnostic at its exact offset instead of being skipped or fabricated as valid.
- Added the Sprint 3 source enrollment and incremental ingestion coordinator (`owner source-enroll --source-id --zone-id --format --format-version --input-file`, `owner source-revoke --source-id`, `owner source-status --source-id`, `owner source-ingest --source-id`): the owner enrolls one exact absolute source fixture at a time — the private locator travels only in the command's input file, never in arguments or reply echoes — with a consistent zone/format/version mapping, and revokes it explicitly. Enrollment, checkpoint and quarantine state persists only as encrypted private vault state beside the existing grant and catalog states, and each source generation's accepted normalized events and byte checkpoint persist together as one encrypted journal resource, so canonical output and checkpoint are durable together and a crash or retry can neither lose nor duplicate events. Ingestion is idempotent and bounded: re-import consumes nothing, appends consume only new complete records, a trailing partial record is never committed as complete, and a replaced or truncated fixture is refused as a generation change instead of being spliced into the prior generation (an explicit owner re-enrollment starts a new generation while the prior journal is preserved). Unknown, revoked, quarantined and unsupported-format sources are refused with explicit diagnostics before the transcript is opened, the agent channel cannot reach any ingestion operation, ingestion requires an unlocked vault and resumes from the persisted checkpoint after lock/restart, and the original fixture bytes and metadata are never modified. That stage shipped the domain-normalization contract that format parsers attach through with no parser of its own; the read-only Codex session adapter (`codex.session.jsonl` version 1) added in this release is the first parser attached through it, and every other format still reports an explicit unsupported diagnostic rather than a best-effort read.
- Added the protected private index: `owner index-status` and `owner index-rebuild` materialize a standard SQLite database (`Microsoft.Data.Sqlite` 10.0.12) held entirely in process memory from the encrypted canonical records, reproducing each resource's ID, revision, zone scope, record kind and state plus its exact referenced IDs (citations, relation endpoints, lifecycle subject/supersession/retained archives). The engine creates no database file, WAL, rollback journal, sort temp or page cache, holds no key, and is discarded on lock and restart; the canonical envelope stays the only truth. Every status read fingerprints the live canonical resource/revision set and reports the materialized generation as stale instead of trusting it, and a rebuild that cannot be proven to describe canonical fails closed with `index_canonical_moved`. The index is owner-only: the agent channel rejects both operations, no index row, count, title, body or embedding is added to any agent reply or to the public catalog, and ranking/search remain future work. Measured on this machine against the frozen Sprint 1 budgets (synthetic 1,000/10,000/100,000-record fixtures at 4 KiB mean body, real service, real named pipe, real owner CLI): the first favorable readings (939.7 records/s at 1,000 and 1,903.3 records/s at 10,000 records) were later established to reflect a warm file cache, and the adverse cache-cold 10,000-record reading (111,511 ms, 89.7 records/s, below the 100 records/second floor) was preserved as ground truth rather than substituted; with the bounded-concurrent batch read, the final binaries rebuild at 518.1 records/s (1,000), 427.1 records/s (10,000, above the 100 records/second floor) and 368.7 records/s in 4.5 minutes (100,000, within the 20-minute bound) in the recorded first-rebuild-after-fixture-aging cache state (no mechanical cache forcing; wall time is not independent OS-miss proof); the service idle working set after warm-up peaks at 237,543,424 B (~226.5 MiB, at most 256 MiB) with idle CPU at 0.003244% of the host; persistent product data is 866,137,705 B (~826 MiB, at most 1.5 GiB) at 100,000 records with the index itself adding 0 persistent bytes and no database/WAL/journal/temp files. Supporting the advertised 100,000-resource size required the encrypted manifest read to use its own size bounds (64 MiB plaintext / 96 MiB envelope, above the 100,000-descriptor worst case) instead of the per-resource 4 MiB envelope cap, and the index rebuild request to carry its own 25-minute pipe timeout instead of the general 10-second request guard (every other request is unchanged).
- Added owner collection membership and the permission-filtered agent collection view (`owner collection-set`/`collections`, `agent.collection.view` on the agent channel, `owner agent-collection-view`): memberships live only in the encrypted owner scope state, and `agent.collection.view` projects a live session's already-frozen approved snapshot into the approved resource IDs and revisions only. The view carries no collection name, member, title, zone, kind, count, total, or paging field, and a session granted a subset of a collection never sees the members it was not approved for. A later membership change, title or path revision, or new zone descendant cannot enter a live view; it advances the policy generation and fails every live session closed instead of silently re-scoping it. Membership grants no read of an unapproved member and no automatic read of a relation, lifecycle record, retained archive, or registered source that merely points at an approved member.

Verified on the real WPF window against the real service and pipes (visual proof), plus a permanent scenario for the owner-channel key path; the UI states the managed-memory erasure and same-account-compromise limits plainly instead of claiming protection.

### Changed

- Changed DeepSeek chat completion wire requests in `OpenAiCompatibleProviderAdapter` to explicitly disable reasoning mode (`"thinking": { "type": "disabled" }`) across all model jobs, preventing reasoning token consumption from exhausting output token caps while preserving S6-T1 compatibility and token bounds.
- Changed the private index rebuild (`owner index-rebuild`) to read canonical envelopes as bounded concurrent batches (up to 128 resources per batch, up to 8 overlapping reads) inside the same counted vault operation, instead of one serial read per envelope. Every per-file security boundary is unchanged: each envelope still goes through its own file reparse/ACL check, AES-GCM AEAD binding, and exact-revision gate; each batch plaintext is zeroized after its rows are inserted (and on any failure), so no more than one batch is ever resident and the shared lifecycle key is never zeroized by the read path. Lock still drains all in-flight operations before clearing the key, and the rebuild's real 25-minute request token cancels it at a batch boundary. Verified on the real service/pipe/CLI at 1,000/10,000/100,000 records (427.1 records/s at 10,000 against the 100 records/second floor, 4.5 minutes at 100,000 against the 20-minute bound, idle working set at most ~226.5 MiB, 0 persistent index bytes, 0 SQLite sidecars) and through an exercised owner lock during an in-flight rebuild (the rebuild completes and publishes first, the lock clears the key afterward, and no private read succeeds after the lock).
- Changed the protected private index schema from 1 to 2 with chained migration (fresh engines walk 0 -> 1 -> 2, existing S2-T7 v1 engines walk 1 -> 2): new memory-only token-posting and temporal tables keyed by resource ID and revision so every indexed revision keeps its own searchable rows and a frozen grant keeps resolving its approved revision after later revisions rebuild. No raw body text is stored; only normalized tokens, titles, kinds, instants, publication state and applicability.
- Changed the owner lock during an in-flight index rebuild to stop that rebuild instead of waiting for it: a requested lock signals the in-flight batch reads to cancel at their batch boundary, the bounded active I/O drains, and only then is the key cleared (the key-lifetime and operation-drain invariants are unchanged — the lock still completes only after the counted operation is disposed). The cancelled rebuild fails closed with a distinct `index_rebuild_cancelled` status and publishes no generation, so it is never confused with the request's own 25-minute timeout, which still surfaces as `request_timeout`. Single reads, writes, and every non-index operation keep their existing drain-only semantics. Before this change, a lock issued during a rebuild longer than the general 10-second request guard returned `request_timeout` to the owner even though the lock had actually executed after draining the whole rebuild (observed at 25.6 s on 10,000 records and 81.7 s on 100,000 records); the same lock now completes in 315 ms with the rebuild cancelled. Verified on the real pipe at 10,000 and 100,000 records, including the same valid read denied only while locked and served again after re-unlock, a fresh-epoch rebuild after the cancellation, overlapping lock requests, and an unchanged tamper fail-closed negative.
