# Changelog

All notable changes to Meta Brain are documented here.

## [Unreleased]

### Added

- Added owner-selected `source-folder-enroll`: owners choose a folder with explicit recursive/include/exclude rules, inspect a bounded metadata-only preview, then confirm once; confirmed members use canonical encrypted source-registry records and the existing encrypted membership index, with exact duplicate enrollment remaining idempotent.
- Added explicit owner `source-folder-refresh-optin`/`source-folder-refresh-optout` consent, default off, for current and future matching regular files under a confirmed folder's stored root/include/exclude and no-reparse/final-path boundaries. Manual and background refresh share the existing incremental coordinator; member pause, revoke and per-source opt-out remain vetoes, lock/folder opt-out cancel active reads before checkpoint commit, and deleted members remain canonical/history as missing rather than being automatically revoked or purged.
- Added owner-controlled raw-byte preservation for Codex/OMP source ingestion: reference-only is the default, explicit source/folder consent carries a retention deadline, and complete unsupported or encoding-invalid records can be retained exactly in the encrypted journal with their checkpoint. Owner status reports availability, preservation, interpretation and derivation separately; OMP version barriers and independently validated chain references remain fail-closed; the owner CLI exports one exact preserved span to a new file only while unlocked. Existing v1 journals remain v1 unless a real v2-only element is written; no agent scope, UI or MCP surface was added.
- Added the MIT License for Meta Brain source and release packages, retaining `Copyright (c) 2026 triet4p` and keeping bundled third-party license terms separate.
- Added a Vietnamese static landing page with product selection, quick starts, scenario navigation, security boundaries, release information and a local-only, checksum-verified candidate preview.

- Added a standalone self-contained Windows CLI setup executable for candidate-specific install, upgrade, reinstall and CLI-only removal. It reuses the shared installation/data-root lifecycle, records frontend ownership and candidate identity, refuses unsafe shared-runtime conflicts, preserves owner data, and does not register PATH, profiles, autostart or services.
- Added a self-contained graphical Windows Owner UI setup executable. Owners can choose application and data locations, install/update or remove only the Owner UI through the shared lifecycle, and optionally open the installed console without a CLI bootstrap.
- Added immutable release-candidate assembly for a dedicated Owner UI setup executable, with a separate setup asset hash, embedded payload/member hashes, exact dependency/license inventory and the shared candidate identity.
- Added an independent self-contained MCP 1.0.0 ZIP with its shared runtime, candidate-bound package manifest, dependency/license notices, stdio entrypoint and Codex/OMP registration details.
- Added the Windows x64 release bundle for the three products and the shared runtime (S9-T6): one self-contained package (`--self-contained true -r win-x64`, so the target machine needs no installed .NET runtime, SDK, repository or PowerShell) with `cli/MetaBrain.Cli.exe`, `owner-ui/MetaBrain.OwnerUi.exe`, `mcp/MetaBrain.Mcp.exe`, the shared host `service/MetaBrain.Connections.exe` and `installer/MetaBrain.Installer.exe`, plus `release-manifest.json` carrying the product version and every file's size and SHA-256. `scripts/release/publish-release-bundle.ps1` builds the stage directory, the zip and the zip's SHA-256 as developer tooling; it is never a runtime prerequisite.
- Added the packaged owner CLI entrypoint `cli/MetaBrain.Cli.exe` (S9-T6): one product entrypoint over the same shared lifecycle and owner commands, with `--help` printing the release layout and `--version` reporting the product version. The installer now requires and installs the `cli/` payload and reports the product version and the three entrypoints, and every product directory resolves the same shared host through one locator.
- Added one product version (1.0.0) for every executable (S9-T6): the CLI and the installer print it (`--version`), the MCP entrypoint prints it on stderr so stdout stays JSON-RPC, the owner console shows it in its title, and `install-state.json` records it.

- Added the owner **Operations & audit** view and its owner-channel operations (S8-T4): `owner health`, `owner audit`, `owner diagnostics` and `owner retention` report, in the owner console and over the owner control pipe, who acted, what they acted on, how it ended, the cost the service already charged and the real error code the service returned, and they give the owner the next action for every recorded failure. All four are owner-only and need the unlocked vault; the agent channel refuses them. The audit trail and the error diagnostics live in one dedicated encrypted file of the vault (`operations-audit.enc`) written with the vault's own data key, they are not a canonical record, they are not indexed by the private index and they are never published — the approved catalog stays the only public disclosure. A new **safe operational log** (`logs/operations.log`) records the operation, the outcome and the error code of every audited act through a sanitizer that replaces anything which is not a short lowercase token with `redacted`, so a credential, a token, a path, a title or a payload cannot reach it; a refusal that happened while the vault was locked is visible there and nowhere private, because the private state exists only inside the unlocked vault and the product never keeps a second key, never auto-unlocks and never buffers a plaintext queue. The owner's retention choice applies to the audit trail and the diagnostics and reports exactly how many entries it removed; a retention request the product refuses removes nothing at all, because the whole request is validated before the first removal, and a purge of a record also removes the audit entries and diagnostics that named it, with tombstones so they are not served again after a restart or a restore — a restore of a backup taken after the purge serves neither, while a copy the owner took before it still holds the entries of its moment. A refused owner operation answers with the real error code the service knows (the code is recorded in the trail, the owner's own sentence stays in the reply), so the trail records the real failure instead of a placeholder, and when the trail itself cannot be written the owner's own act is still answered and the failure is reported truthfully in the safe operational log as `audit_persistence_failed`.

- Added the owner vault format upgrade (S8-T3): `owner upgrade` (and `owner upgrade-with-recovery-code`) raises a vault written by an older version to the content schema this build writes — the owner scope-grant control state and the canonical lifecycle and model job records — while keeping every record's ID, revision, zone, attribution, relations, lifecycle state and archive, and keeping the key envelope, passphrase and recovery key byte-for-byte unchanged. The act runs only while the vault is locked, leaves it locked, keeps an encrypted rollback point of the files it rewrote, and resumes after an interruption instead of losing work. `owner rollback` restores that point (only the files unchanged since the upgrade) and `owner rollback --discard true` drops it; `owner status` reports the stored format and whether a rollback point is available without a credential. The owner console shows the same card in **Backup & export**.

- Added the owner **Backup & export** view (S8-T2): the encrypted backup, the clean restore and the explicit readable export are now owner acts in the owner console, not only owner-channel commands. The owner picks the backup file, the restore source, the clean restore folder and the export file with the Windows file and folder pickers, and picks the export scope from the records the service ranks by title — including the sources those records cite, so a citation to a record outside the scope stays withheld whole and nothing enters the scope without the owner choosing it. The restore credential travels in exactly one request and the field is cleared right after it; locking the vault, losing the service or ending the session clears the chosen paths, the export selection and the credential field, and a late answer can never restore them. The backup and the export need the unlocked vault, the restore works while the vault is locked, and a restore never replaces the live vault or writes into a folder that already exists.
- Added encrypted backup, clean restore and owner-scoped plaintext export (S8-T2): `owner backup --control-pipe --output-file <file>` writes one encrypted snapshot of the unlocked vault together with the vault's wrapped key envelope, and never the data key, a credential, a token, a session or any readable record content; the snapshot is captured under the same gate every vault read and write takes, so it is one consistent point in time and a write that arrives during the capture waits and then commits normally. `owner restore` and `owner restore-with-recovery-code` rebuild that snapshot into a directory that must not exist yet, keeping every record, its exact revision, its relations, sources, lifecycle and intention states, its archive and retained revisions and the fact that something was deleted; the restored vault opens with the owner's own passphrase or recovery key because the envelope travels with the backup instead of being re-keyed. A restore brings back no live grant, no agent session and no redeemable token, a token that was already used stays used, and the private index is rebuilt from the restored canonical records instead of being copied. A wrong passphrase, a lost key, a tampered container and a truncated container all fail closed: nothing is written, no partial vault is left, no key is re-issued and no recovery is faked. `owner export --resource-ids ... --output-file ...` writes a readable plaintext file that holds exactly the records the owner selected, withholds a citation to a source outside that selection whole (no source, locator or span leaves the vault) and states in its own header what it withheld; the file is written once, never over an existing file, and a copy that was already taken is not revoked by a later purge, lock or export.

- Added the per-user installation and the locked daily lifecycle (S8-T1): `MetaBrain.Installer.exe install|start|stop|restart|status|health|autostart|uninstall` lays the application down for the current owner account, starts the service host locked, keeps the vault and the rest of the owner's data out of the installer's reach, and preserves the vault, the source snapshots, the backups and the recovery material when the application is removed. The install needs no administrator rights, no AppContainer and no patched agent runtime; the login autostart is an explicit opt-in that writes one per-user Run value. Every start begins locked, an owner unlock is explicit, and a restart, a logout or a reboot brings the vault back locked with no agent session resurrected. The private paths the product creates on the daily path carry the ordinary permissions of the owner account, and on that path the product never changes the permissions or the owner of a path: the privacy of the data comes from the owner-controlled key, the authenticated encryption around every persisted record, the vault lock and the owner-approved catalog, token and scoped-session APIs, and the owner channel and the agent pipe accept the owner account only. The inherited legacy migration command (`owner migrate`) still applies an owner-only access rule and takes the owner of the migrated settings file; it is not on the daily path, it was not exercised, and it must not be run while it still mutates permissions.

- Added one shared instance lifecycle every frontend uses (S9-T2): `MetaBrain.Connections.exe lifecycle {start|stop|restart|status|connect} --config <service-settings.json> | --data-root <dir>` resolves, creates (clean root only) or selects the instance and starts or connects the same locked host. A clean root needs no hand-written settings; an existing root is kept byte-identical with its pipe endpoints; concurrent starts serialize so two launches never produce two writers; an endpoint answered by a different live host is refused as `endpoint_occupied` instead of aliased. Truthful readiness/version/path/conflict/unavailable errors carry remediation; stop/restart drain through the core and lock the vault with no surviving session; closing a frontend never stops the shared host. The installer service commands delegate to the same lifecycle.

- Added the owner console product with integrated first-run startup (S9-T4): `owner-ui/MetaBrain.OwnerUi.exe` opens with no instance selected and no running service, and the Owner session view selects/creates the data-root folder, starts the same shared locked host every frontend uses, and connects the owner session — with check/restart/explicit stop and truthful recoverable next actions; closing the console never stops the shared host. Owner workflows run fully in the console over the existing shared operations with no new domain semantics: memory write plus body revise, verdicts, snapshot purge, direct subject-lifecycle create and transitions, and every accepted coverage area (provision/recovery/unlock/lock, zone/collection, source mapping/enroll/ingest/refresh/preservation, capture/read-back, library/detail/evidence/history/revise/index recovery, proposals, relations, sharing, provider/jobs/schedules in consent, intentions/review/lifecycle/archive/purge, audit/diagnostics/retention, backup/restore/export and upgrade). Credentials travel only through PasswordBox fields into one request each with lock/disconnect/inflight clearing; closing never kills another frontend's host.
- Added a dedicated packaged MCP client entrypoint (`mcp/MetaBrain.Mcp.exe`) that starts/connects the shared locked host and exposes the existing scoped agent tools without CLI preparation or owner authority; proposal/feedback drafts cross the owner channel on stdin rather than plaintext temporary files. Scoped snapshot reads now return the preserved snapshot's exact bytes (strict-UTF-8 text, or an `application/octet-stream` blob for binary content) alongside the metadata line instead of metadata alone.
- Added the complete CLI product for existing owner workflows (S9-T3): `MetaBrain.Connections.exe` now opens with grouped entrypoint help and every `owner` command documents its exact inputs via `owner --help` / `owner <verb> --help`. Nine previously UI-only operations are bridged through existing shared operations with no new domain semantics: `owner library` (ranked owner search with zone/collection/kind/level/currentness/time/paging filters), `owner proposal-publish` / `proposal-reject` (pending-proposal review with attribution and revision gates), and `owner intentions` / `intention-trigger-set` / `intention-trigger-clear` / `intention-context-set` / `intention-context-disable` / `intention-schedule-run` (intention schedule reads and trigger acts). Capture commands (`memory-create`, `memory-revise`, `source-create`, `source-revise`, `research-capture`, `feedback-create`, `relation-create`, lifecycle writes, proposal review) accept friendly scalar options (`--body`, `--title`, `--cite id@rev[:start-end]`, `--target id@rev`, `--from`/`--to`, `--reason`, `--due-at`, `--project`/`--task`) that build the exact draft the service reads, so no workflow requires hand-assembled JSON; the exact draft file (`--input-file`) stays as the advanced path for owner-owned data. Credentials still travel only through secure interactive prompts (vault passphrase, recovery key, provider key) and destructive or authority-minting acts still require typed confirmations; every failure stays truthful with the owner next action.
- Added the owner review queue and review-after reconciliation (S7-T6): `owner review-list` reports the items whose review-after deadline has passed, whose cited source moved past the revision the item cited, whose cited source is gone, or whose cited source states that it is unavailable, and `owner review-record --resource-id --reason` records that the owner looked. A moved, missing or unavailable source is reported as a fact about the evidence, never as a denial of the item's belief: the review act writes only the owner's own encrypted review state (`review-state.enc`), so the item keeps its own text, evidence, citations, revision and states, no intention is completed, and no grant, collection or session is touched. A deadline known only as a year stays a year and is reported as undetermined, and an availability nobody asserted stays unknown, so stale, unknown and unavailable never collapse into one another. The owner's answer is bound to what they were looking at: a reason stays settled while the cited source keeps its revision and the review-after deadline keeps its stamp, and it asks the owner again as soon as either one changes. The owner **Review queue** view shows the service's own reasons with the exact source ID, cited revision, live revision and availability.
- Added owner purge with derivative impact handling (S7-T5): the owner dry-runs the exact impacted canonical set (`owner purge-preview --resource-id --resource-revision --reason`), confirms exactly that set with typed `PURGE` (`owner purge-confirm --purge-id --resource-id --resource-revision --target-zone --target-kind --impacted id|revision|kind|reason,... --live-generation N [--catalog-ids ...] --reason`), and resumes an interrupted confirm (`owner purge-resume --purge-id`). The service deletes exactly the bound canonical copies (target plus lifecycle, archives, relations, citing proposals/items, feedback, journals, preserved snapshots and snapshot lineage), withdraws the mapped catalog entries, strips the purged IDs from grants/collections/pending requests with a policy-generation bump, clears the materialized private index, and records the durable encrypted purge ledger without the removed payload. Changed targets, mistyped confirmations, agent purge calls and resurrected IDs fail closed; retained encrypted backups keep ciphertext until their own retention and a restore must re-apply the ledger.
- Added the owner recall policy for tiered, explainable forgetting (S7-T4): the owner demotes, pins, sets aside or restores a memory item through explicit owner acts (`owner recall-apply --resource-id --act {demote|pin|archive|restore} [--reason]`, `owner recall-read --resource-id`) recorded in one new encrypted owner state file (`recall-policy.enc`) beside the scope-grant, catalog and source-enrollment states. The policy never writes canonical content: an item's body, evidence, verification, citations, revision and attribution are untouched, nothing is deleted, and no grant, collection or session scope is read or written by an act. Demote and set-aside require the owner's own reason, a pinned item cannot be demoted or set aside until the owner releases that protection with an explicit restore, and no read count is recorded anywhere: reading an item more often never raises its truth or its priority, and an infrequent item is never lowered automatically. The policy applies only to subjects a caller already holds in scope — an archived item is not offered by the scoped search, the scoped brief or the default owner library and returns through an explicit expansion (`includeArchived` on `owner agent-search`/`owner agent-brief` and on the owner library, or the `metabrain_memory_search`/`metabrain_memory_brief` MCP tools) or the history view; a demoted item stays findable but sorts below the items the owner did not demote; a pinned item sorts with the protected items first. In the brief, a set-aside item is not projected but is named in the omission trace (`owner_archived`) instead of vanishing silently, and the MCP bridge offers no recall act to the agent channel, so no agent can change the owner's forgetting decision. Every served hit now carries the owner's disposition and a ranking reason that names only the facts that actually moved it, and the owner's own rationale stays on the owner channel. The owner Library view gained the recall block (read state, demote, pin, set aside, restore) and an include-archived filter; a restore returns visibility only and never widens a scope.

- Added durable one-time intention time triggers and the owner **Intentions** view (S7-T2): owners create, reschedule and cancel exact offset-qualified ISO-8601 due instants through the owner channel; the service's no-LLM background pass records each due notification once, catches up after an offline/locked deadline only after explicit unlock, and keeps notification, acknowledgement and completion separate. The exact trigger and markers live in the existing encrypted lifecycle record; v1 records without triggers and v2 records with time triggers decode as current lifecycle schema v3 while preserving any due instant. Locked scheduling and due-list reads pause without disclosing private metadata or unlocking the vault. Date-only and timezone-free local timestamps (including ambiguous repeated-hour values) plus invalid offsets are refused; an explicit numeric offset selects the intended instant, while named-zone recurrence and clock-correction guarantees are not implied.
- Added owner-controlled project/task intention triggers to the **Intentions** view and scoped brief (`owner agent-brief --context-project --context-task`, `metabrain_memory_brief` `contextProject`/`contextTask`, S7-T3): reminders are returned only for enabled, pending, unacknowledged intentions whose exact current item ID/revision is already in the caller's frozen `memory.context` grant and whose configured owner labels match the explicitly supplied context. Context labels remain encrypted in lifecycle schema v3; v1 and v2 records decode without contextual triggers, with v2 due instants preserved. Reads do not mutate lifecycle state, acknowledgement never completes, disabling stops contextual reminders, a new intention/member/revision does not expand an existing grant, and lock or scope denial returns no private context or intention content.
- Added temporal recall and decision history end-to-end (S7-T1): `current`/`history`/`as-of` query over the existing encrypted validity/revision semantics on both the owner library and the scoped agent search (`owner agent-search --as-of`, `metabrain_memory_search` `asOf`), plus the owner Library as-of filter and the per-item decision-history/retained-revision view. Current excludes withdrawn/rejected, past-validity and superseded items; history keeps them with original reasons; as-of replays recorded history only through a UTC non-future instant. Coarse stamps without a zone bound nothing, unknown stays unknown, bounds are inclusive, and unresolved contradictions never resolve by newest-wins.
- Added the owner **Jobs** view and its owner-channel operations (`owner.provider.status`, `owner.schedule.set`, `owner.schedule.disable`, `owner.schedule.status`, `owner.schedule.run`): the console runs one bounded job from an explicit selection (each input pinned to a revision) or a batch of one bounded job per selected note, shows every job's real state, recorded scope, provider-reported usage and failure with a cancel that releases a queued job's pre-send reservation and sends nothing, reads the encrypted spend ledger, stores the model/egress settings with the frozen caps and never echoes the API key back, and enables or disables the owner's synthesis schedule. Saving or reading a note still reaches no provider: the same screen's capture act writes one encrypted source and only a run the owner starts reaches a provider.
- Added the owner-enabled synthesis schedule: one encrypted record (`sec-synthesis-schedule` in the vault's system zone) holding the owner's explicit input selection, objective, requested level, destination, provider/model and interval, written and read through the owner channel. An enabled schedule is evaluated by a background pass that runs the same bounded synthesis job the owner can start by hand, at most one run per due instant; the next due instant is always computed from the moment a run finished, so slots missed while the vault was locked, while the service was down or while a previous run was still executing are never replayed as catch-up runs, and a locked vault pauses the schedule instead of unlocking anything. Disabling keeps the configuration, clears the next due instant and stops all further scheduled runs, and the stored schedule survives a service restart.

- Added owner declassification into an explicit shared zone (`owner declassify-preview`, `declassify-publish --destination-id --destination-zone`, `declassify-proposal-publish --resource-id --resource-revision --destination-id --destination-zone`): the owner previews the exact sanitized body, title, metadata and citation set beside the pinned private sources, then explicitly publishes with a typed PUBLISH confirmation. The shared copy is an ordinary revision-gated memory item with zero citations; private lineage travels only through encrypted accepted `derived_from` relations unreadable from shared-only sessions. Catalog publication stays a separate act that never opens a body, frozen grants never gain the new item, forged owner/user intent stays inert, and a moved private root marks the derivative with a generic `derivative_source_changed` warning without disclosing private identifiers or rewriting the conclusion. The owner console Inbox review surface gains a matching declassification panel on the same session and service calls.
- Added explicit bounded multi-level synthesis (`--profile synthesis` on `owner job-create`, with a selection draft passed as `--input-file`): the owner names every input (each pinned to one revision), the objective, and the requested level (`l2` or `l3+`), and the job produces pending synthesis proposals carrying `MemoryKind.Synthesis`, the owner's level, assistant authorship, reported-source evidence, and one citation per grounded input at the revision it read. A synthesis job requires at least two distinct inputs, an owner objective, and a level; an `l3+` request additionally requires a selected input that is itself an `l2`/`l3+` synthesis item. Every selected input is revalidated before the private read, before the provider send, and before the commit, so a source that moved or was revoked blocks the next step and releases the reservation; a selected input set whose pinned citation lineage revisits the same resource is refused by the same bounded lineage walk the review uses. Each item must ground in verbatim passages of the exact inputs it names (an item spanning inputs must ground in two distinct inputs), and neither the level nor the number of cited inputs upgrades evidence. `owner job-*` output now lists the pinned inputs, objective, and level, and `owner proposal-read` reports whether the sources a pending proposal cites still match (`CITATIONS state=current|needsReview reasons=... stale=...`).
- Added a computed citation review to the owner review surface: a pending proposal whose cited source moved, disappeared, became unavailable, or was revoked is served as needing review, naming the cited resource, and the same evaluation walks a cited memory item's own pinned citations with the bounded lineage policy the job scope uses, so a root that changed or was revoked underneath an unchanged cited item is served as `citedSourceLineageChanged` instead of the output reading as current; a cyclic or unbounded lineage is reported rather than read as current. The proposal's content, revision, level, and citations are never rewritten and no citation is silently re-pinned. The owner console shows this in the review pane, which serves the first cited input it can read beside the content — a registered source's exact revision text, or a cited memory item's exact body at the revision the citation pins through the same owner detail read the library uses — and reports a revision the service does not serve as a refusal instead of substituting another revision or resource, while listing every citation with its pinned revision. Stored single-source job records are migrated on read to the current input-set scope instead of becoming unreadable.
- Added research-note and trend structuring profiles to the existing bounded model-job path: research asks the model to separate source-reported claims and limitations, observations, user hypotheses, questions and explicit intention proposals; the trend prompt limits analysis to the selected source revision and asks the model not to treat repeated mentions or citations of one origin as independent confirmations. Both request source citations, grounded excerpts and explicit offset-qualified occurrence times where present; outputs remain pending owner review. These semantic instructions do not guarantee correct interpretation. URLs are not fetched and proposals are not auto-published.

- Added the coding-session structuring profile (`--profile coding-session` on `owner job-create`): structures normalized coding-session transcripts into pending proposals across problem, attempt, result, decision, and lesson kinds in the destination inbox without auto-promotion. Enforces strict attribution separation (assistant claims never override observed tool results; passing local tests never infers production deployment via `unverified_inference` fail-closed checks), preserves known project, environment, and commit/version conditions in proposal applicability while keeping unknown fields null (`applicability_ungrounded` fail-closed checks), anchors every proposition to complete verbatim excerpts with exact byte-level source spans (`SourceSpan(Start, End)` in memory source references), supports dual source reading from both registered sources and source snapshots, and ensures hostile directives inside transcripts remain inert with zero execution authority.
- Added scoped model job execution and provider egress controls (`owner job-create`, `job-start`, `job-cancel`, `job-status`, `job-list`, `job-ledger`, `provider-config`): jobs execute with immutable scope snapshots revalidated before source access, provider call, and proposal commit; enforce pre-send caps of 10,000 input tokens using a formally grounded full-request bound (tied directly to wire JSON serialization in `OpenAiCompatibleProviderAdapter.BuildRequestJson` with cited primary-source DeepSeek-V4.1-Flash 1M context, ByteLevel BPE with complete 256-byte coverage proving at most 1 token per UTF-8 byte, and official Jinja2 chat template delimiters using U+2581 separators and 30-token thinking mode framing bound at 32 tokens, denying unapproved models, tokenizers, or context limits with `unknown_context`), 2,000 output tokens, $0.25 per job, and $5.00 rolling 30-day budget with historical $0.0054 reserve; require exact provider pricing cards (unknown pricing/context denies); output boundary validates strict JSON schema and verbatim source text grounding, generating strictly inert proposals with fixed non-owner attribution and no shell, grant, or key authority; ambiguous post-send failures (abrupt connection drops after accept, non-success HTTP errors, malformed response JSON, missing usage) strictly retain budget reservations in the encrypted spend ledger while only proven-not-sent pre-send denials release reservations; actual billable tokens from completed calls are committed to the ledger with usage cap violations failing closed without erasing spend; source enrollment validation (`ValidateSourceEnrollment`) enforces fail-closed behavior across all phases: corrupt or unavailable enrollment metadata truthfully refuses job creation before private read, fails closed before send with reservation safely released, and fails closed before commit preserving ledger spend with zero proposals committed and source text preserved intact; true source revocation (`source-revoke`) between create and start fails closed and releases pre-send reservation, and mid-flight revocation before commit revalidates source availability, halting execution and aborting proposal commit while preserving source and committing billable spend; in-flight cancel, timeout, and restart recovery halt execution and retain unknown reservations in the encrypted spend ledger; credentials and spend ledger persist encrypted in the vault with secure in-process `.env` or secret input and no secret argument exposure. Live provider execution was verified under explicit affirmative owner authorization using product model `deepseek-flash` on the agreed synthetic research note, establishing real token accounting (256 in / 482 out, conservative local rate calculation $0.0006552 USD), proposal commit with inert assistant attribution, reservation release and settlement in the encrypted spend ledger, and persistent readback of the same job, proposal, and source across service restart and owner unlock.
- Added explicit owner-selected preservation and exact availability tracking for enrolled external sources (`owner source-status`, `source-relocate`, `source-snapshot-list/preserve/read/retain/purge`): status fingerprints the exact enrolled bytes rather than trusting size/mtime, reports missing/changed/unreadable without scanning or following another path, and advances registered-source availability revisions. Relocation requires an explicit owner-supplied candidate whose full bytes match the enrolled generation anchor; snapshots are opt-in encrypted canonical resources with retention and purge tombstones, and the original external file is never written, moved or deleted by product code.
- Added owner ingestion operations and safe background refresh for enrolled sources (`owner source-list`, `source-pause`, `source-resume`, `source-refresh-optin/optout`, `source-refresh` alongside the existing `source-status`/`source-ingest`/`source-relocate`/`source-revoke`): the allowlist listing reports each source with its life, checkpoint, refresh consent and actual encrypted cache scope (journal/snapshot ciphertext sizes and snapshot revision) without echoing private locators; pause stops status reads, ingest and refresh with no transcript open; an owner-opt-in background loop advances opted-in sources without a manual command while unlocked, running one idempotent incremental pass over the allowlist only for opted-in sources and skipping every other source with an explicit reason and no read; a requested lock cancels the in-flight pass at its next per-source boundary and pause/disable stop reads with no checkpoint movement; revoke stops refresh and explicit re-enrollment starts a new generation on a fresh checkpoint; lock and restart deny every private read and refresh with no plaintext queue, and unlock resumes persisted checkpoints and consent without duplicates. Diagnostics carry bounded codes only, with no transcript, locator or secret.
- Added owner research capture of verbatim unstructured text (`owner research-capture --resource-id --zone-id --input-file` with optional `--title`/`--source-url`/`--source-author`/`--source-date`, read back with `owner research-read --resource-id [--resource-revision --output-file]`): the note text is persisted encrypted as one registered source through the existing source registry before any structuring or model job could run, so capture needs no provider, never fetches or validates the URL, classifies nothing, and keeps omitted URL/author/date unknown instead of inferring them. The captured note keeps its declared origin role, reads back byte-for-byte after restart and unlock, anchors downstream citations at its live revision, and never exposes its text on the metadata source wire. While the vault is locked the capture is refused with `vault_locked` — nothing reports saved and no plaintext draft or queue is written — and the agent channel cannot reach either command.
- Added the read-only Codex session adapter (format `codex.session.jsonl` version 1) on the existing enrollment and incremental ingestion coordinator: the shipped service now interprets real Codex rollout sessions, keeping each record's declared attribution (only a `message` record declaring role `user` is stored as a user statement; tool calls stay assistant-authored, tool outputs stay tool-authored, runtime notifications and control records stay system-authored), its timestamp, the session identity, the exact consumed source span and a digest of the exact record bytes, with no message body ever copied into Meta Brain. - Fixed the private index rebuild stamping the live canonical digest onto another generation's rows (S8-T5). The rebuild published its snapshot with the digest of the live canonical set while the row count and the row sample came from whatever generation the engine had loaded, so a generation that was substituted between the publish and the read could be reported as a current generation. The rebuild now checks that the generation the engine holds is the generation of the live canonical set and discards the pass if it is not, and the owner index status applies the same check, so a substituted generation is reported as stale instead of being served as current. The answers, the ranking and the filters are unchanged.


- Fixed the private index handing out-of-scope candidates back to the caller for a large scope (S8-T5). A scope of more than 900 approved resources is bound in the engine's own in-memory scope table, and the candidate query now joins that table, so the scope filter runs inside the engine's SQL and an out-of-scope resource ID never leaves the engine at all. - Fixed indexing a document into a private index that had been upgraded from the previous index schema (S8-T5). The engine kept its own count of document identities, so the first document indexed after the upgrade was handed an identity the migrated rows already held and the write failed with a duplicate-identity error. - Fixed the owner channel client dropping the real code of a refused owner act (S8-T4). The service answers a refusal with the real error code in `errorCode` and the owner's own sentence in `error`, but the client read the `error` text as the code, so a refused job, schedule or recall act reached the owner console as a free-text sentence in the code position (`code: No approved pricing card found for …`) and the real code (`pricing_unknown`) was lost.
