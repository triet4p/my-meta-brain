# Changelog

All notable changes to Meta Brain are documented here.

## [Unreleased]

### Added

- Added the read-only Codex session adapter (format `codex.session.jsonl` version 1) on the existing enrollment and incremental ingestion coordinator: the shipped service now interprets real Codex rollout sessions, keeping each record's declared attribution (only a `message` record declaring role `user` is stored as a user statement; tool calls stay assistant-authored, tool outputs stay tool-authored, runtime notifications and control records stay system-authored), its timestamp, the session identity, the exact consumed source span and a digest of the exact record bytes, with no message body ever copied into Meta Brain. Append, incomplete tails, re-import, restart and replacement behave as the coordinator already specified, and any record or payload shape the adapter has not observed and cannot match to the upstream definition is refused with an explicit named diagnostic at its exact offset instead of being skipped or fabricated as valid. Sessions larger than the 16 MiB per-run snapshot bound are refused explicitly rather than partly read.
- Added the read-only OMP session adapter (format `omp.session.jsonl` version 1) on the existing enrollment and incremental ingestion coordinator: the shipped service now interprets real OMP agent sessions, keeping each record's source-declared attribution (a `message` declaring role `user` is stored as a user statement only when the record itself declares attribution `user`; role `assistant` stays assistant-authored; role `toolResult` stays tool-authored; `custom_message` follows its declared `user`/`agent` attribution; title, session, custom envelopes, config changes, credential pins and compaction stay system-authored), its UTC timestamp (envelope ISO-8601, message-body epoch-millis), the session identity and cwd context, the declared id/parentId chain with the compaction `firstKeptEntryId` boundary, the exact consumed source span and a digest of the exact record bytes, with no message body ever copied into Meta Brain. Append, incomplete tails, re-import, restart and lock/unlock behave as the coordinator already specifies, and any record, role, content-part, stop-reason, attribution or version shape outside the observed schema is refused with an explicit named diagnostic at its exact offset instead of being skipped or fabricated as valid.
- Added the Sprint 3 source enrollment and incremental ingestion coordinator (`owner source-enroll --source-id --zone-id --format --format-version --input-file`, `owner source-revoke --source-id`, `owner source-status --source-id`, `owner source-ingest --source-id`): the owner enrolls one exact absolute source fixture at a time — the private locator travels only in the command's input file, never in arguments or reply echoes — with a consistent zone/format/version mapping, and revokes it explicitly. Enrollment, checkpoint and quarantine state persists only as encrypted private vault state beside the existing grant and catalog states, and each source generation's accepted normalized events and byte checkpoint persist together as one encrypted journal resource, so canonical output and checkpoint are durable together and a crash or retry can neither lose nor duplicate events. Ingestion is idempotent and bounded: re-import consumes nothing, appends consume only new complete records, a trailing partial record is never committed as complete, and a replaced or truncated fixture is refused as a generation change instead of being spliced into the prior generation (an explicit owner re-enrollment starts a new generation while the prior journal is preserved). Unknown, revoked, quarantined and unsupported-format sources are refused with explicit diagnostics before the transcript is opened, the agent channel cannot reach any ingestion operation, ingestion requires an unlocked vault and resumes from the persisted checkpoint after lock/restart, and the original fixture bytes and metadata are never modified. That stage shipped the domain-normalization contract that format parsers attach through with no parser of its own; the read-only Codex session adapter (`codex.session.jsonl` version 1) added in this release is the first parser attached through it, and every other format still reports an explicit unsupported diagnostic rather than a best-effort read.
- Added the protected private index: `owner index-status` and `owner index-rebuild` materialize a standard SQLite database (`Microsoft.Data.Sqlite` 10.0.12) held entirely in process memory from the encrypted canonical records, reproducing each resource's ID, revision, zone scope, record kind and state plus its exact referenced IDs (citations, relation endpoints, lifecycle subject/supersession/retained archives). The engine creates no database file, WAL, rollback journal, sort temp or page cache, holds no key, and is discarded on lock and restart; the canonical envelope stays the only truth. Every status read fingerprints the live canonical resource/revision set and reports the materialized generation as stale instead of trusting it, and a rebuild that cannot be proven to describe canonical fails closed with `index_canonical_moved`. The index is owner-only: the agent channel rejects both operations, no index row, count, title, body or embedding is added to any agent reply or to the public catalog, and ranking/search remain future work. Measured on this machine against the frozen Sprint 1 budgets (synthetic 1,000/10,000/100,000-record fixtures at 4 KiB mean body, real service, real named pipe, real owner CLI): the first favorable readings (939.7 records/s at 1,000 and 1,903.3 records/s at 10,000 records) were later established to reflect a warm file cache, and the adverse cache-cold 10,000-record reading (111,511 ms, 89.7 records/s, below the 100 records/second floor) was preserved as ground truth rather than substituted; with the bounded-concurrent batch read, the final binaries rebuild at 518.1 records/s (1,000), 427.1 records/s (10,000, above the 100 records/second floor) and 368.7 records/s in 4.5 minutes (100,000, within the 20-minute bound) in the recorded first-rebuild-after-fixture-aging cache state (no mechanical cache forcing; wall time is not independent OS-miss proof); the service idle working set after warm-up peaks at 237,543,424 B (~226.5 MiB, at most 256 MiB) with idle CPU at 0.003244% of the host; persistent product data is 866,137,705 B (~826 MiB, at most 1.5 GiB) at 100,000 records with the index itself adding 0 persistent bytes and no database/WAL/journal/temp files. Supporting the advertised 100,000-resource size required the encrypted manifest read to use its own size bounds (64 MiB plaintext / 96 MiB envelope, above the 100,000-descriptor worst case) instead of the per-resource 4 MiB envelope cap, and the index rebuild request to carry its own 25-minute pipe timeout instead of the general 10-second request guard (every other request is unchanged).
- Added owner collection membership and the permission-filtered agent collection view (`owner collection-set`/`collections`, `agent.collection.view` on the agent channel, `owner agent-collection-view`): memberships live only in the encrypted owner scope state, and `agent.collection.view` projects a live session's already-frozen approved snapshot into the approved resource IDs and revisions only. The view carries no collection name, member, title, zone, kind, count, total, or paging field, and a session granted a subset of a collection never sees the members it was not approved for. A later membership change, title or path revision, or new zone descendant cannot enter a live view; it advances the policy generation and fails every live session closed instead of silently re-scoping it. Membership grants no read of an unapproved member and no automatic read of a relation, lifecycle record, retained archive, or registered source that merely points at an approved member.
- Added a domain lifecycle and temporal-validity surface over the shared encrypted vault (`owner lifecycle-create`, `lifecycle-read`, `lifecycle-retained-read --resource-revision`, and the owner acts `lifecycle-publish`/`lifecycle-reject`/`lifecycle-withdraw`/`lifecycle-repropose`, `lifecycle-question-resolve`/`lifecycle-question-reopen`, `lifecycle-intention-complete`/`lifecycle-intention-cancel`/`lifecycle-intention-supersede`, `lifecycle-intention-notify`/`lifecycle-intention-acknowledge`, `lifecycle-validity-set`, and `lifecycle-retain --expected-revision`). A lifecycle record is a revision-gated canonical resource under a reserved `lc-<subject>` ID derived from the subject memory item, so exactly one record covers one subject and the zone, kind, initial states, executor, and revision are always derived server-side from the subject envelope, the trusted context, and the vault descriptor — never from a request body. Publication (proposal/published/rejected/withdrawn) moves only through explicit acts carrying the actor, a UTC time, and a recorded rationale in an append-only history; a question is never resolved by an AI answer or an `addresses` relation, only by an explicit resolve/reopen; `notified`/`acknowledged` are separate markers and never a done state; supersession names the replacing item explicitly and a conflicting supersession is refused instead of overwriting the recorded replacement. Occurred, recorded, validity bounds, and review-after stamps keep their precision, timezone offset, and unknown exactly as known, and an unknown time is never fabricated into a date. Historical revisions stay genuinely retrievable through the real service: an explicit `lifecycle-retain` act copies the exact live revision bytes into a derived `arc-<subject>-r<N>` archive resource on the same encrypted store, `lifecycle-retained-read` serves that historical envelope with both revisions, and a grant over the archive never reaches the live item or a newer revision. Saving or revising an AI-written note keeps its author, creation method, and evidence level, and only a user-authored record can carry user-confirmed evidence.
- Added typed relations (`owner relation-create`, `relation-accept`/`relation-reject`/`relation-unlink`/`relation-relink --expected-revision`, `relation-read`, scoped `agent.link.create`/`agent.relation.read`) stored as revision-gated canonical ciphertext on the shared vault: each record carries a stable relation ID, two endpoints with their verified kind and the exact revision the link was made against (plus an optional evidence span), the relation kind, creator/executor, creation method, rationale, UTC times, and a proposed/accepted/rejected lifecycle with a recorded unlink state. `derived_from` and `supersedes` form one derivation DAG so pure and mixed cycles are refused, while `related_to` may cycle. When an endpoint moves to a new revision or a cited registered source stops being available, the link and its transitive dependents are reported as needing review without rewriting the stored link or the owner's conclusions. Relation reads authorize the exact relation ID/revision plus both endpoints, so a cross-zone or ungranted endpoint is denied generically with no endpoint metadata, count, or backlink.
- Added an encrypted registered source registry (`owner source-create`, `source-revise --expected-revision`, `source-read`, scoped `agent.source.read`) that persists only source metadata (title, private locator, version, explicit availability, executor/method, UTC captured/recorded times) as revision-gated canonical ciphertext on the shared vault, with no source body and originals left untouched. Memory items cite registered sources by ID with the live source revision and an optional validated span checked at write time; stale, unregistered, or boundary-invalid citations fail closed, and a stored anchor remains a truthful historical record after the source is revised. Item read grants never authorize the source API: an item-only grant serves citations without registry title/locator/version, while an explicit `source.read` grant opens only its frozen resource/revision.
- Added an owner-controlled encrypted vault with passphrase/recovery-key provisioning, explicit v1 settings/data migration, locked startup, authenticated managed-resource reads/writes, and a lock that drains active private responses.
- Added distinct owner-control and agent pipes with schema-2 settings migration, atomic encrypted scope-state migration, consume-before-disclose single-use bearer redemption, process-local epoch-bounded sessions, expiry/policy invalidation, and owner-controlled scope inspection through DPAPI-protected local handoffs.
- Added owner-only active-session listing and selective revocation plus agent-channel authorization decisions for exact frozen operations and resource/revision scopes. Lock, expiry, and policy-generation changes deny stale sessions; only the per-job `$0.25`, 10,000-input-token, and 2,000-output-token ceilings are enforced at this boundary. Agent-supplied egress remains denied without a trusted provider adapter/pricing context; no provider call or `$5/30-day` rolling-spend ledger is implemented.
- Added agent-channel scoped resource reads (`agent.resource.read` plus `owner agent-read`) that authorize the exact frozen operation, resource ID, and revision before and after opening the encrypted vault bytes, then re-validate the live registration before serving. Denied, unknown, malformed, path-like, cross-scope, reparse-redirected, and ungranted `source.read` requests share one generic `resource_unavailable` denial; revoke, expiry, policy-generation, lock, and restart invalidate warm reads and old ses…
 - Added owner-reviewed access requests and approval (`owner request/request-status` on the agent pipe plus `owner requests/request-preview/request-approve/request-reject`): agents request published catalog IDs with purpose and declared provider/disclosure context and receive only an opaque receipt/status, while owners preview exact resource revisions/bodies/raw-source scope/disclosure on an attached owner console with redirected output refused and no preview file written, narrow without enlarging scope, and mint single-use scoped tokens through DPAPI-protected handoffs with stale-preview, replay, and lock/restart fail-closed behavior.
 - Added a headless agent-channel surface for scoped sharing: `owner agent-catalog-list` on the agent pipe plus an `agent-mcp` stdio bridge (MCP 2025-11-25 `initialize`/`tools/list`/`tools/call`) exposing only catalog discovery, access request/status, handoff-path redemption, session inspection, and scoped reads. The bridge holds no vault/key/ciphertext, mints no grants, rejects raw bearer material in arguments, and redacts bearer-shaped output. Scoped reads return the exact approved body in memory (strict-UTF8 text, else lossless base64 blob) with no default plaintext file; the A3 count-only/file proof is superseded by actual A4 body consumption plus A5 same-client revoke/fresh-lock denials. Official Codex 0.159.2 and OMP 18.6.0 walkthroughs ran on synthetic fixtures under owner walkthrough-only consent (task still [~], fresh review/checkpoint Pending): each client drove catalog, access request, handoff-path redemption, granted read, session inspection, revoke-denied and fresh-never-revoked lock-denied reads through the same client on its own scope, with guessed/private-ID, unselected-resource, body-spoof, `source.read` escalation, unknown-tool, and raw-bearer negatives failing closed; keys/raw bearers never entered model context, while approved synthetic bodies did per the consent.
- Added durable encrypted canonical writes with revision-gated `memory.create` (create-only), `memory-revise`/`memory-import`/`resource.write --expected-revision` (live-revision only), staged-ciphertext-before-manifest commits, unlock-time recovery that reaps interrupted staged bytes and temp files, and an explicit owner import boundary replacing external plaintext editing of canonical files. Stale, duplicate, mismatched, tampered, truncated, swapped, wrong-key, and locked writes fail closed with no half-published state.
### Changed

- Changed the private index rebuild (`owner index-rebuild`) to read canonical envelopes as bounded concurrent batches (up to 128 resources per batch, up to 8 overlapping reads) inside the same counted vault operation, instead of one serial read per envelope. Every per-file security boundary is unchanged: each envelope still goes through its own file reparse/ACL check, AES-GCM AEAD binding, and exact-revision gate; each batch plaintext is zeroized after its rows are inserted (and on any failure), so no more than one batch is ever resident and the shared lifecycle key is never zeroized by the read path. Lock still drains all in-flight operations before clearing the key, and the rebuild's real 25-minute request token cancels it at a batch boundary. Verified on the real service/pipe/CLI at 1,000/10,000/100,000 records (427.1 records/s at 10,000 against the 100 records/second floor, 4.5 minutes at 100,000 against the 20-minute bound, idle working set at most ~226.5 MiB, 0 persistent index bytes, 0 SQLite sidecars) and through an exercised owner lock during an in-flight rebuild (the rebuild completes and publishes first, the lock clears the key afterward, and no private read succeeds after the lock).
- Changed the owner lock during an in-flight index rebuild to stop that rebuild instead of waiting for it: a requested lock signals the in-flight batch reads to cancel at their batch boundary, the bounded active I/O drains, and only then is the key cleared (the key-lifetime and operation-drain invariants are unchanged — the lock still completes only after the counted operation is disposed). The cancelled rebuild fails closed with a distinct `index_rebuild_cancelled` status and publishes no generation, so it is never confused with the request's own 25-minute timeout, which still surfaces as `request_timeout`. Single reads, writes, and every non-index operation keep their existing drain-only semantics. Before this change, a lock issued during a rebuild longer than the general 10-second request guard returned `request_timeout` to the owner even though the lock had actually executed after draining the whole rebuild (observed at 25.6 s on 10,000 records and 81.7 s on 100,000 records); the same lock now completes in 315 ms with the rebuild cancelled. Verified on the real pipe at 10,000 and 100,000 records, including the same valid read denied only while locked and served again after re-unlock, a fresh-epoch rebuild after the cancellation, overlapping lock requests, and an unchanged tamper fail-closed negative.

### Removed

- Removed the protected Codex/OMP launcher, AppContainer and per-session credential bindings, and legacy session CLI commands. The service no longer claims OS-level agent sandboxing; CR01 exposes only a separate scope-limited agent session protocol. MCP/client/resource-retrieval integration remains future work.
