# Operations — installing and running Meta Brain every day

Meta Brain is installed for **one owner account** on Windows. The owner installs it, starts it,
unlocks it, and uses it; the agents connect to it as scoped clients. Nothing in this runbook needs
administrator rights, an AppContainer, a patched agent runtime, or an account of its own.

- Product scope and requirements: [`META-BRAIN.md`](META-BRAIN.md), [`REQUIREMENTS.md`](REQUIREMENTS.md).
- Sprint plan and acceptance for this work: [`sprint-plans/sprint-8.md`](sprint-plans/sprint-8.md).

## 1. The two roots

| Root | Holds | Removed by |
| --- | --- | --- |
| **Install root** — e.g. `%LOCALAPPDATA%\MetaBrain\App` | The application files: `cli/`, `service/`, `owner-ui/`, `mcp/`, `installer/`, and `install-state.json` (which also records the product version) | `uninstall` |
| **Data root** — e.g. `%LOCALAPPDATA%\MetaBrain\Data` | The owner's private data: `service-settings.json`, `vault/`, the runtime state (`runtime/`), the source snapshots, the backups and the recovery material | **never** by the installer |

The two roots are separate on purpose: an upgrade replaces the application files and leaves the
data alone, and an uninstall removes the application and keeps the data. The two roots must not
overlap: the installer **refuses** a data root inside the install root and the other way round,
because an uninstall removes the install root and would take the data with it. Give the two roots
sibling directories, as in the example above (`…\MetaBrain\App` and `…\MetaBrain\Data`). A data
root *inside* the install root (`…\MetaBrain` and `…\MetaBrain\data`) is refused with
`The data root must not live inside the install root: an uninstall removes the install root.`

On the daily path — `install`, `start`, `stop`, `restart`, `status`/`health`,
`uninstall`, the owner unlock and the agent session — the product **does not change the
permissions of a path**: it creates the data root, the settings file, the vault directory and its
envelopes, the runtime directory and its log with the ordinary permissions of the owner account,
and it never takes ownership of a path. No custom ACL, DACL, SDDL, filesystem-owner gate, or
permission/ownership mutation exists on any product or verification path. The privacy of the
owner's data comes from the key the owner controls, the authenticated encryption around every
persisted record, the lock of the vault and the owner-approved catalog, token and scoped-session
APIs — not from the access rights of the file system. The owner channel and the agent pipe are two
local-only endpoints that each accept the owner account only; a pipe is created with the default
security descriptor of the service process and rejects remote clients by its pipe mode, which is
not a change to the permissions of an existing path. Whether a connected client may act as owner
is decided by the authenticated impersonated-client check in the service, not by pipe or
filesystem permissions.

**The inherited legacy cutover, outside the daily path.** The legacy migration command
(`cli\MetaBrain.Cli.exe owner migrate --config <legacy-settings.json>`) creates the encrypted
vault from the inherited plaintext settings and resource files, writes the current settings file,
and only then removes the plaintext copies it migrated. It is not reachable from the daily path —
the service refuses a legacy settings file with `Legacy plaintext settings require the explicit
owner migration command before service startup.` It applies **no access rule and takes no
ownership**: the migrated data is protected by the owner's key and the encrypted envelopes, exactly
like the rest of the vault. The service must be stopped. A cutover interrupted after the vault
exists and before the settings write is resumed by the same command when the passphrase opens the
new vault and every legacy record is still byte-identical; otherwise it refuses untouched. The
recovery key was shown by the interrupted run and is not shown again.

## 2. Install

```text
MetaBrain.Installer.exe install --payload <published-payload-dir> --install-root <dir> --data-root <dir> [--component cli|owner-ui|mcp|all] [--start]

- `--payload` — the published application: `cli/MetaBrain.Cli.exe`,
  `service/MetaBrain.Connections.exe`, `owner-ui/MetaBrain.OwnerUi.exe`,
  `mcp/MetaBrain.Mcp.exe`, `installer/MetaBrain.Installer.exe`. The release
  bundle's own layout is exactly this payload.
- `--install-root` — where the application files go.
- `--data-root` — where the owner's private data goes. It is created with the ordinary permissions
  of the owner account. It must be a **sibling** of the install root, not a directory inside it
  (§1): the installer refuses overlapping roots.
- `--control-pipe` / `--agent-pipe` — optional fixed endpoint names. Without them the installer
  generates random ones. Fixing them lets the owner point a client at a known endpoint; an upgrade
  keeps the endpoints an existing installation already uses.
- `--start` — start the service right away.

A first install with sibling roots, exactly as the runbook intends it:

```text
MetaBrain.Installer.exe install --payload <published-payload-dir> --install-root %LOCALAPPDATA%\MetaBrain\App --data-root %LOCALAPPDATA%\MetaBrain\Data
```

An install **never creates the vault**: the first start is locked and uninitialized, and the owner
creates the vault explicitly (§4). Installing over an existing install root is an upgrade of the
application files; the data root, the vault and the pipe endpoints are kept.

### 2.1 The release bundle (S9-T6)

The bundle is one self-contained Windows x64 package with a directory per product entrypoint and
one for the shared runtime, plus the installer that consumes the same layout:

```text
cli\MetaBrain.Cli.exe               owner CLI (--help, --version, lifecycle, owner commands)
owner-ui\MetaBrain.OwnerUi.exe      owner console
mcp\MetaBrain.Mcp.exe               agent MCP server over stdio
service\MetaBrain.Connections.exe   shared runtime host (started by the shared lifecycle)
installer\MetaBrain.Installer.exe   per-user install/upgrade/uninstall
release-manifest.json               product version, runtime identifier, every file's size and SHA-256
```

The bundle is a `--self-contained true -r win-x64` publish, so the target machine needs no .NET
SDK, no installed .NET runtime, no repository and no PowerShell: unpack it and run the entrypoints.
Its product version is the version every entrypoint reports (`--version`; the console shows it in
its title; the installer records it in `install-state.json`).

A developer builds the bundle from a checkout with
`powershell.exe -NoProfile -File scripts\release\publish-release-bundle.ps1`. That script is
developer tooling and never a runtime prerequisite: it writes the stage directory, a zip and the
zip's SHA-256 under `runtime\release` by default, and changes no host state (no installation, no
service registration, no autostart entry, no registry value, no environment or profile change and
no permission change).

### 2.2 Immutable release candidates and CLI setup (S10-T2/T3)

From a reviewed source checkout, assemble the candidate with a dedicated,
self-contained CLI setup executable and an independent MCP package:

```powershell
powershell.exe -NoProfile -File scripts\release\assemble-candidate.ps1
```

The command writes an immutable candidate directory under ignored
`runtime\release-candidates`. The CLI asset is a standalone unsigned setup EXE;
launch it for an interactive install/upgrade, or use
`MetaBrain-CLI-...exe install --install-root <dir> [--data-root <dir>]`.
At the confirmation prompt, enter `n` or `q` to cancel before setup changes any files.
The installed entrypoint is `cli\MetaBrain.Cli.exe`; use its full path with
`--help` or `--version`. Setup supports `uninstall --install-root <dir>` and
removes only the CLI component, keeping the shared runtime while another
registered frontend depends on it and always preserving the selected data root.
It does not change PATH, profiles, autostart, services, registry, permissions or environment
settings. The self-contained single-file .NET host may extract runtime support under
`%TEMP%\.net\<bundle>\<hash>` on launch; this is runtime temp data, not an install or profile
registration.

### 2.3 Graphical Owner UI setup (S10-T4)

Download the candidate-specific `MetaBrain-OwnerUI-...exe` setup executable. It opens a graphical setup window where the owner selects separate application and data locations, installs or updates only the Owner UI component through the shared installer, and may open `owner-ui\MetaBrain.OwnerUi.exe` after installation. Setup can also remove only the Owner UI; other registered components keep the shared runtime, and the data location is always retained.

The setup is self-contained for Windows x64 and requires no SDK, repository, command prompt, CLI bootstrap, or installed .NET runtime. The window supports keyboard navigation; Escape or Cancel closes setup before an operation begins. Once installation or removal starts, setup keeps the operation intact and reports the shared installer's actual success or refusal. It does not start or unlock the service. Setup is unsigned: SHA-256 checks bytes but does not authenticate the publisher. It temporarily extracts its embedded payload under the current user's `%TEMP%` and removes the staging directory when possible; the single-file host may also extract runtime support under `%TEMP%\.net`. No PATH, profile, service, registry, permission, environment or autostart changes are made.

The Owner UI installer and CLI installer use the same installation identity, component state, runtime version and data root. If the other frontend is already installed, use the recorded data location; setup refuses a different data root or an incompatible shared candidate/version rather than replacing the other component's runtime.

To recheck an existing candidate's asset hashes and file sets:

```powershell
powershell.exe -NoProfile -File scripts\release\assemble-candidate.ps1 -VerifyOnly -CandidateDirectory <candidate-directory>
```

Candidate identity records two different things. `source.head` is the Git HEAD the
assembly ran from. `source.sourceTreeSha256` is a **SHA-256 content digest of the
source population the assembler read from the worktree**, not a Git tree object and
not the commit's tree ID. The assembler enumerates
`git ls-files --cached --others --exclude-standard`, drops the fixed excluded roots
(`artifacts/`, `runtime/`, `dist/`, `build/`, `out/`, `.git/`, `docs/PLAN.md`,
`docs/sprint-plans/sprint-10.md`, `scripts/sprint-6/__pycache__/`), sorts the
remaining paths, and hashes the UTF-8 text of one line per file in the form
`<file SHA-256><two spaces><relative/path>`, joined by newlines. The population is
therefore the tracked files at HEAD **plus every untracked file Git does not ignore
at that instant**: uncommitted edits to tracked files and untracked non-ignored
files both contribute, and the candidate manifest records
`source.workingTreeIncluded=true` for that. For the frozen 1.1.0 candidate the
population included uncommitted planning documents (`docs/ROADMAP-2.0.md`,
`docs/POST-1.0-DIRECTION.md`, `docs/sprint-plans/sprint-11.md` through
`sprint-18.md`) and a Python bytecode cache under `scripts/sprint-11/__pycache__/`.
The value binds the assembly base HEAD plus that dirty worktree snapshot, not the
separately approved source checkpoint commit, and it cannot be recomputed once any
population file changes; it is not a Git object ID at all. Uncommitted source
therefore does not masquerade as the HEAD revision, and a matching digest is not a
signature: the candidate is unsigned. The CLI and graphical Owner UI setups embed
their exact staged component/shared-runtime payloads and store the same candidate
identity with shared install state. A different candidate or runtime version is
refused when another frontend is registered; install the matching complete
candidate or remove the other frontend before replacing the shared runtime.
Rebuilds receive new IDs and never overwrite a candidate. Candidate manifests
record both setup assets and embedded payload hashes, dependency inventories,
licenses and unsigned status; SHA-256 does not authenticate the publisher. Public
release remains owner-controlled and is not authorized.

An unpacked developer bundle can still be passed to the shared installer's
`--payload` command for a full-component install. An entrypoint run from the
unpacked directory uses the `service\MetaBrain.Connections.exe` beside it.

## 3. The daily commands

Every service command below is run from the installed copy in `<install root>\installer`; it
accepts `--install-root <dir>` to address another installation. The installed `uninstall` command
acts on its own installation and optionally accepts `--component`; the dedicated CLI setup has
its own CLI-only uninstall command (§8), and the graphical Owner UI setup provides its own Owner UI-only removal surface (§2.3).

```text
MetaBrain.Installer.exe start        # start the service host (locked)
MetaBrain.Installer.exe stop         # clean stop: the host drains, locks the vault and exits
MetaBrain.Installer.exe restart      # stop and start again
MetaBrain.Installer.exe status       # health: service, vault state and process
MetaBrain.Installer.exe health       # the same report as status
```

`status` exits with `0` when the owner channel answers and with a non-zero code when it does not,
so it can be used as a health check. The report contains the install root, the data root, the
settings file, both pipe endpoints, the running process (pid plus whether it is still that
process), the service state and the vault state.

The stop is a *request*, not a kill: the installer asks the host to stop, waits for the process to
exit and confirms the exit. The host identifies itself with its pid **and** its start time, so a
recycled pid is never mistaken for the running host.

### 3.1 The shared instance lifecycle (S9-T2)

Every frontend — the packaged CLI, the owner console and the agent bridge — resolves the same
instance (one data root, one settings file, one pair of pipe endpoints) and starts or connects
the same locked host through one shared implementation. The installer service commands above
delegate to that same lifecycle, so no frontend keeps a second start/stop/status path.

```text
cli\MetaBrain.Cli.exe lifecycle start --data-root <dir>     # create (clean root only) or select, then start the shared locked host
cli\MetaBrain.Cli.exe lifecycle status --data-root <dir>    # health from the real owner channel; exits non-zero when unreachable
cli\MetaBrain.Cli.exe lifecycle connect --data-root <dir>   # prove the shared host is reachable without starting it (T3–T5 share this gate)
cli\MetaBrain.Cli.exe lifecycle stop --data-root <dir>      # explicit drain, lock and exit; the only act that ends the shared host
cli\MetaBrain.Cli.exe lifecycle restart --data-root <dir>   # stop and start again: fresh locked host, no surviving session
```

Each verb also accepts `--config <service-settings.json>` instead of `--data-root <dir>`. A clean
root needs no hand-written settings file: `start` creates it with fresh endpoints. An existing
root is kept byte-identical — pipe endpoints an owner already configured in a client never move,
and no vault, snapshot, backup or recovery material is touched. Concurrent starts serialize on
the instance, so two launches never produce two writers; an endpoint answered by a different live
host is refused as `endpoint_occupied` instead of aliased. Every failure is truthful with the next
action (`version_mismatch`, `host_exited`, `host_unresponsive`, `start_timeout`, `stop_failed`,
`invalid_settings`, `instance_not_initialized`, `transport_unavailable`). Closing a frontend never
stops the shared host, and no frontend stops another frontend's host implicitly.

### 3.2 The owner CLI (S9-T3)

The packaged CLI is `cli\MetaBrain.Cli.exe`: `--help` prints the product identity and the release
layout, `--version` prints the product version, `lifecycle` verbs (§3.1) cover setup, and `owner`
verbs cover every owner workflow. It runs in any terminal (PowerShell, cmd, or another console);
running a CLI command is normal use, not glue. What the CLI never requires: hand-written settings
or internal JSON, PowerShell helper scripts, the owner console, or direct vault writes. The exact
draft file (`--input-file`) stays as the advanced path for owner-owned data only.

```text
cli\MetaBrain.Cli.exe --version                              # the product version every entrypoint reports
cli\MetaBrain.Cli.exe --help                                 # release layout, usage and exit codes
cli\MetaBrain.Cli.exe owner --help                           # every workflow group
cli\MetaBrain.Cli.exe owner <verb> --help                    # exact inputs of one command (`owner help --command <verb>` is the same)
```

Capture commands accept friendly scalar options that build the exact draft the service reads, so
no workflow needs hand-assembled JSON: `--body`/`--title`/`--kind`/`--author`/`--method`/
`--evidence`/`--level`/`--cite id@rev[:start-end]` for memory items, `--text` for research notes,
`--target id@rev`/`--kind`/`--note` for feedback, `--kind`/`--from id@rev`/`--to id@rev`/`--reason`
for relations, `--reason`/`--replacement` for lifecycle acts, `--due-at`/`--project`/`--task` for
intention triggers. Previously console-only operations are CLI verbs with the same semantics:
`owner library` (ranked search with zone/collection/kind/level/currentness/time/paging filters),
`owner proposal-publish` / `proposal-reject` (attribution and revision gates), `owner intentions`
and the `intention-trigger-*` / `intention-context-*` / `intention-schedule-run` acts.

Credentials travel only through secure interactive prompts — the vault passphrase, the recovery
key and the provider key are never option values, environment values, config entries, log lines
or model context. Destructive or authority-minting acts print a frozen preview and require a
typed confirmation (`ISSUE`, `SET`, `PUBLISH`, `APPROVE`, `REJECT`, `PURGE`). Request bodies are
shown only on an attached owner console: `owner request-preview` refuses redirected output
(`preview_redirect_denied`), and the bound `owner request-approve` runs there with the preview
the console showed. Exit codes are truthful: `0` done, `2` usage (nothing changed), `3`
refused/locked/unavailable/denied, `4` invalid input or unwritable output, `5` a job that ended
without completing, `1` transport or unexpected failure.

### 3.2.1 MCP client registration (standalone package 1.1.0; installed 1.0.0 unchanged)

The 1.1.0 release includes a standalone self-contained MCP ZIP. Extract the complete archive into
a stable directory while preserving its folders; for example, choose
`%LOCALAPPDATA%\MetaBrain\MCP\<version>\`, replacing `<version>` with the release you installed
(`1.1.0` here; use `1.0.0` only for the earlier release). This package is
separate from the CLI and Owner UI setup executables, and does not require either frontend to be
installed, an SDK, a repository, an installed .NET runtime or PowerShell.

```text
mcp\MetaBrain.Mcp.exe
service\MetaBrain.Connections.exe
package-manifest.json
RELEASE-NOTES.txt
THIRD-PARTY-NOTICES.txt
licenses\...
```

Register the absolute extracted path to `mcp\MetaBrain.Mcp.exe` as a `stdio` command. The
`service\MetaBrain.Connections.exe` shared runtime is packaged beside it and is selected
automatically; do not point a client at the service executable. Supply exactly one instance
selector: `--data-root <owner-data-root>` or `--config <service-settings.json>`. Use the
owner-selected data root also used by any existing owner frontend. On first startup a clean root
receives ordinary nonsensitive settings and the shared host starts locked; an existing instance
keeps its settings and endpoints. Closing MCP does not stop the shared host.

MCP only exposes existing agent-scoped operations. It never provisions or unlocks a vault,
publishes catalog entries, approves/rejects requests, issues tokens or purges data. The owner
performs those acts through the CLI or Owner console. Never place keys or bearer tokens in client
configuration; only DPAPI-protected handoff/session-file paths cross MCP.

Run `mcp\MetaBrain.Mcp.exe --version` or `--help` from the extracted package to print the
entrypoint identity and usage on stderr. Neither writes informational text to stdout, which stays
reserved for JSON-RPC. Startup diagnostics are sanitized and go to stderr.

Sprint 9 T7 accepted compatibility evidence observed Codex CLI `0.164.0` and Oh My Pi `18.12.6`
with this stdio package. These are evidence versions, not a claimed minimum/maximum support
range. MCP negotiates `2025-11-25`, `2025-06-18`, `2025-03-26` or `2024-11-05`; absent or
unknown client offers use `2025-11-25`. No client version range is asserted. The package manifest
records the observed client versions, protocol revisions, layout, dependencies and known limits.

Register it with each client's supported scoped configuration; do not edit user/profile settings
or use `mcp add` / `/mcp add`. Replace `<owner>` and `<isolated-workspace>` with real paths.
This Codex CLI example uses documented process-scoped `-c` overrides and does not submit a
prompt:

```text
codex -C "<isolated-workspace>" -c 'mcp_servers.metabrain.command="C:\\Users\\<owner>\\AppData\\Local\\MetaBrain\\MCP\\<version>\\mcp\\MetaBrain.Mcp.exe"' -c 'mcp_servers.metabrain.args=["--data-root","C:\\Users\\<owner>\\AppData\\Local\\MetaBrain\\Data"]'
```

For OMP, create `.omp/mcp.json` only inside an isolated workspace, not the product repository
or a user-level configuration directory, then start OMP with that workspace and `--no-session`:

```json
{
  "mcpServers": {
    "metabrain": {
      "type": "stdio",
      "command": "C:\\Users\\<owner>\\AppData\\Local\\MetaBrain\\MCP\\<version>\\mcp\\MetaBrain.Mcp.exe",
      "args": ["--data-root", "C:\\Users\\<owner>\\AppData\\Local\\MetaBrain\\Data"]
    }
  }
}
```

```text
omp --cwd "<isolated-workspace>" --no-session
```

The selected `--data-root` and executable paths are plain filesystem paths; JSON strings escape
backslashes, while Codex `-c` values are quoted as shown. To use an existing settings file,
replace the two-element `--data-root` argument pair with `["--config","<settings-file>"]`.
These examples describe registration only; they do not replay client/product workflows.

### 3.2.2 Approving one agent request in the CLI (one owner frontend)

The agent sees only catalog metadata and receives an opaque request ID from
`metabrain_access_request`. The owner completes the decision in the CLI; no script, no PowerShell
helper and no second frontend are involved:

```text
cli\MetaBrain.Cli.exe owner requests --control-pipe <pipe>
cli\MetaBrain.Cli.exe owner request-preview --control-pipe <pipe> --request-id <request id>
cli\MetaBrain.Cli.exe owner request-approve --control-pipe <pipe> --request-id <request id> --preview-id <preview id> --operations memory.read,memory.search --expires-at-utc 2026-11-01T00:00:00Z --handoff-file <new file>
```

- `request-preview` prints the exact resources, revisions, operations and bodies. It must run in
  the attached terminal: redirected output is refused with `preview_redirect_denied` so reviewed
  bodies never reach disk.
- `--operations` must be a subset of the operations the preview printed. Omitting it narrows the
  approval to `resource.read`; a request that asked for `memory.read`/`memory.search` is then
  refused as `request_invalid` because the approval would not match what was requested. Copy the
  previewed operations you intend to approve (for example `memory.read,memory.search`).
- `--resource-ids` is optional narrowing; omitting it approves every previewed resource.
  `--destination-resource-ids` and the provider fields apply only when the preview declared them.
- `--expires-at-utc` requires an explicit UTC instant (`Z` or `+00:00`). `--handoff-file` must be a
  new path; the typed `APPROVE` mints the single-use token into that DPAPI-protected file. Give
  the path to the agent, which redeems it with `metabrain_redeem` into its own session file.

### 3.2.3 Owner-selected folder source enrollment (S11-T2)

This section describes 1.1.0 (S11-T2) folder enrollment, released 2026-11-01; an installed 1.0.0
binary keeps its earlier fail-closed behavior and does not offer this surface.

Use the owner CLI only with an unlocked vault. Select one absolute folder and declare recursion and include/exclude globs explicitly; `--exclude-globs none` means no exclusions. The preview is bounded and metadata-only. Type `ENROLL` once to confirm the exact preview; any other input or end-of-input cancels without changing membership.

```text
cli\MetaBrain.Cli.exe owner source-folder-enroll --control-pipe "<pipe>" --folder "<absolute-folder>" --zone-id <zone> --format <format> --format-version <N> --recursive true|false --include-globs "<glob[,glob...]>" --exclude-globs "<glob[,glob...]|none>"
```

Include globs are required. Each include/exclude list allows at most 16 unique relative patterns of at most 256 characters; patterns cannot contain absolute paths, drive/colon syntax, `.` or `..` segments. `*`, `?` and `**` are supported. Enumeration stops at 512 visited entries, and every included locator must fit the source registry's 512-character limit.

Only the selected root is examined; Meta Brain does not scan home/profile folders. A selected root is refused if any component from its volume root through the selected folder is a reparse point. Reparse entries found below the selected root are excluded, and their targets are never admitted. Confirmation re-enumerates the preview and reads selected files only through the existing bounded source reader to record anchors; it registers encrypted source metadata, not source bodies. A duplicate is idempotent only when the confirmed selection and membership still match. Later matching files require explicit folder-level refresh consent; `ENROLL` confirmation is not refresh consent and folder refresh is default off.

Before creating canonical source records, enrollment writes their opaque IDs to the existing encrypted source-enrollment state. If enrollment is interrupted, unlock removes any still-uncommitted records before granting vault operations. If a storage failure prevents in-process cleanup and the command reports `source_folder_recovery_pending`, further vault operations remain refused in that unlocked epoch; resolve the storage failure, then run `owner lock` followed by `owner unlock` so recovery can retry. The recovery marker contains IDs only, not source content or paths.

Enumeration and source reading are separate filesystem operations. The reader's final-path/handle checks narrow the race and fail closed when the path changes, but do not eliminate every time-of-check/time-of-use window.

### 3.2.4 Codex/OMP source ingestion and raw preservation (S11-T3)

This section describes the 1.1.0 (S11-T3) source implementation, released 2026-11-01; an installed
1.0.0 binary keeps its earlier fail-closed behavior and does not offer these surfaces.

Ingestion is owner-only and runs while the vault is unlocked. `source-status`/`source-list`
report four separate facets: current availability, whether exact bytes are stored (`preserved` or
`reference_only`), achieved interpretation, and derivation (`not_indexed`). Reference-only sources
remain source-dependent; if an unsupported complete record or invalid UTF-8 is encountered without
preservation consent, the checkpoint stops at its byte offset and status reports the diagnostic,
unprocessed bytes and source dependency. No unknown record becomes an event or gains attribution.

```text
cli\MetaBrain.Cli.exe owner source-status --control-pipe "<pipe>" --source-id <id>
cli\MetaBrain.Cli.exe owner source-ingest --control-pipe "<pipe>" --source-id <id>
cli\MetaBrain.Cli.exe owner source-raw-preservation-optin --control-pipe "<pipe>" --source-id <id> --retain-until-utc <UTC-instant>
cli\MetaBrain.Cli.exe owner source-raw-preservation-optout --control-pipe "<pipe>" --source-id <id>
cli\MetaBrain.Cli.exe owner source-preserved-record-read --control-pipe "<pipe>" --source-id <id> --offset <byte-offset> --output-file "<new-file>"
```

The opt-in is a distinct owner act, not an interpretation setting; it requires a future UTC
retention deadline. `source-folder-enroll` also accepts `--raw-preservation-until-utc <UTC-instant>`
to explicitly apply that consent to members of the confirmed folder selection. Without the flag,
members remain reference-only. Opting out stops preserving future records; already preserved spans
remain owner-readable through their own stored retention deadlines. Each preserved span keeps the
`retainUntilUtc` it was written with, and that deadline is an expiry for read-back, not a purge:
once it passes, `source-preserved-record-read` for that offset is refused with
`source_preserved_record_expired`, while the encrypted bytes stay in the journal, `source-status`
keeps listing the span with its deadline, and the four status facets do not change; expiry removes
nothing by itself and an explicit owner action (a purge) is still required to delete the span.
Opting out before the deadline therefore does not shorten the
stored retention and does not delete the span.

With active consent, complete unsupported records (including invalidly encoded input) are copied
byte-for-byte into the encrypted generation journal in the same atomic write as the checkpoint;
ordinary unknown records may then be passed, but an OMP newer-version barrier keeps the checkpoint
at the barrier and stores the entire remaining tail without interpreting it. Exact offsets and
digests are retained; diagnostics contain only a code and offset. OMP parent references are
accepted only from independently validated envelopes. No lossy transcode is attempted.

The read command requires an unlocked owner vault and a new output path; it verifies the stored
digest and writes the exact span without sending source bytes to stdout. These operations are not
available on an agent/MCP surface. Fully supported reference-only sources continue using journal
v1; v2 is written only when a real v2-only element (preserved bytes or a preserved version barrier)
is present. Existing v1 journals are not rewritten merely because consent is enabled; an existing
v2 journal is never automatically downgraded.

### 3.2.5 Folder membership refresh (S11-T4)

This section describes the 1.1.0 (S11-T4) owner behavior, released 2026-11-01; an installed 1.0.0
binary keeps its earlier fail-closed behavior and does not offer this surface.

Enrollment confirmation adds only the exact previewed member metadata. To let the shared manual
and background refresh pass discover current or future matching regular files, explicitly opt in
the persisted folder ID printed by `source-folder-enroll`:

```text

cli\MetaBrain.Cli.exe owner source-refresh --control-pipe "<pipe>"
cli\MetaBrain.Cli.exe owner source-folder-refresh-optout --control-pipe "<pipe>" --folder-id <folder-id>

```

Folder refresh is off by default. Opt-in covers only files beneath that stored root which satisfy

checkpoint as an existing member. `source-list` and `source-status` report `folderId` and

canonical/history data or purging a journal. A deleted member stays enrolled and reports missing.
Per-source refresh opt-out, pause and revoke remain vetoes after folder consent; folder opt-out and
vault lock cancel an active refresh at its read boundary, zero any partial snapshot, and do not
advance the checkpoint. Raw-byte preservation remains separate consent with its own retention
deadline; folder refresh consent alone does not enable it. The background pass is the same shared
coordinator and does not scan outside an opted-in folder selection.

## 4. The locked start and the owner unlock

Every start of the host begins **locked**. The key lives only in the unlocked process memory, so:

- no agent session survives a restart: the session is process memory, not a file.

The owner unlocks explicitly:

```text
cli\MetaBrain.Cli.exe owner provision --control-pipe <control-pipe>   # first time only
cli\MetaBrain.Cli.exe owner unlock   --control-pipe <control-pipe>
cli\MetaBrain.Cli.exe owner lock     --control-pipe <control-pipe>

`provision` asks for the vault passphrase twice and prints a one-time recovery key; store that key

The owner console (`owner-ui/MetaBrain.OwnerUi.exe`) drives the same operations.

### 4.1 Encrypted backup, restore and owner-scoped export

Three owner acts live on the owner control channel. They are owner-only: the agent channel refuses
them, and no agent can mint, widen or reuse any of them.

```text
# 1. One encrypted snapshot of the unlocked vault
cli\MetaBrain.Cli.exe owner backup --control-pipe <control-pipe> --output-file <backup file>

# 2. Restore that snapshot into a clean directory
cli\MetaBrain.Cli.exe owner restore --control-pipe <control-pipe> \
    --backup-file <backup file> --target-directory <directory that does not exist yet>
cli\MetaBrain.Cli.exe owner restore-with-recovery-code --control-pipe <control-pipe> \
    --backup-file <backup file> --target-directory <directory that does not exist yet>

# 3. Export the records you selected as one readable plaintext file
cli\MetaBrain.Cli.exe owner export --control-pipe <control-pipe> \
    --resource-ids <id>,<id> --output-file <file> \
    [--include-relations true] [--include-lifecycle-states true]
```

**In the owner console.** The same three acts are on the console view **Backup & export**
(`owner-ui\MetaBrain.OwnerUi.exe --control-pipe <control-pipe>`), so the owner never has to type an
operation, a resource ID or a path:

- **1. Encrypted backup** — pick the file with *Choose file…* (or type the path) and choose
  *Create encrypted backup*. The vault has to be unlocked; the file is written once and an
  existing file is never overwritten.
- **2. Clean restore into a new folder** — pick the backup file, pick the folder the restored
  vault should go into (it must not exist yet), choose *Owner passphrase* or *Recovery key*, type
  the credential and choose *Restore into the new folder*. The credential travels in that one
  request and the field is cleared right after it. A restore works while the vault is locked,
  because it opens a backup file and writes a new folder instead of reading the live vault. The
  live vault is never replaced: to work with the restored copy, point a vault directory setting at
  it.
- **3. Explicit readable export** — search for the records you want to copy out, choose them by
  their title in the ranked list, and — if the records cite a source — choose the cited source the
  service names, because a citation to a source outside your selection is withheld whole. Then pick
  the file and choose *Write the readable copy*. The file is plaintext, it is written once, and a
  copy that has left the vault is not revoked by a later lock, purge or export.

Locking the vault, losing the service or ending the owner session clears this view: the chosen
paths, the export selection and the credential field go with it, and no answer that was already in
flight can restore them.

**What the backup file is.** One file that holds the encrypted snapshot and the wrapped key
envelope of the vault. It never holds the data key, a passphrase, a recovery key, a token, a session
or any record content in readable form: the snapshot is sealed with the vault's data key, and the
envelope in the file is the same passphrase-wrapped and recovery-wrapped key the live vault header
already holds. A backup file on its own opens nothing; a backup file **together with your
passphrase or your recovery key** opens your data, which is exactly the same boundary as the live
vault. Keep backups where you would keep the recovery key.

**What a restore does.** It reproduces your data — every record, its exact revision, its relations,
its sources, its lifecycle and intention states, its archive and retained revisions, and the fact
that something was deleted — into a directory that must not exist yet. The restored vault opens with
your own passphrase or your own recovery key, because the restore carries the owner's key envelope
and never re-keys it. The restored vault carries **no live authority**: no scope grant, no agent
session and no redeemable token comes back, and a token that was already used stays used. The
private index is not restored either; the derivative is excluded from the backup, so the restored
vault has no published generation and the first search asks for `owner index-rebuild`.

**What fails closed.** A wrong passphrase, a wrong recovery key, a lost key, a tampered container
and a truncated container all refuse the restore, write nothing, leave no partial vault behind and
never reset, re-key or invent a recovery. A refused restore leaves no target directory at all. There
is no fallback key and no "recovered" mode: if you have lost both the passphrase and the recovery
key, the backup cannot be opened.

**Compatibility.** The backup format is versioned (`metabrain/vault-backup` v1) and the restore
reads the version it writes. A backup taken by this build restores with this build. A future format
change must keep reading the older backups or state plainly that it does not; no backup is
silently dropped.

**Retention.** The product does not delete your backups for you. A backup keeps its own ciphertext
until you delete that file yourself, and a backup taken before a purge still holds the ciphertext
of what was purged: the purge ledger names what was deleted, and a restore re-applies that ledger
instead of resurrecting the purged records. Deleting a backup file is the only way to remove that
copy.

**The export is a disclosure, and it cannot be taken back.** The export file is plaintext and holds
exactly the records you selected, in full, as the vault stores them. A citation to a source outside
your selection is withheld whole — neither the source, its locator nor its span leaves the vault —
and the export says in its own header how many citations, relations and records it withheld. The
file is written once and never over an existing file. A copy that was already made is not revoked
by a later purge, a lock or another export: the vault can delete the record, not the copy you took
out of it.

### 4.2 Vault format upgrade, interruption recovery and rollback

A vault written by an older version still opens. Its records keep the content schema they were
written with, and the owner raises them to the format this build writes with one owner act:

```text
cli\MetaBrain.Cli.exe owner upgrade --control-pipe <control-pipe>
cli\MetaBrain.Cli.exe owner upgrade-with-recovery-code --control-pipe <control-pipe>
cli\MetaBrain.Cli.exe owner rollback --control-pipe <control-pipe> [--discard true]
cli\MetaBrain.Cli.exe owner rollback-with-recovery-code --control-pipe <control-pipe> [--discard true]
```

The act runs only while the vault is **locked** — the service is running, the vault is locked and
no private operation is in flight — takes the passphrase or the recovery key, and leaves the vault
locked. It rewrites only the files whose stored content schema is older than this build writes: the
owner scope-grant control state (v2/v3 to v4) and the canonical lifecycle (v1/v2 to v3) and model
job (v1 to v2) records. Every record keeps its resource ID, zone, attribution, relations, lifecycle
state, archive references and exact revision; the key envelope and the manifest are not rewritten.
The envelope and manifest format stay 1: this is a content-schema upgrade, not an envelope change,
and no key is re-wrapped.

**Interruption.** Before the first rewrite the act copies every file it will change into an
encrypted rollback point at `<vault>\rollback\<upgrade id>\`: those copies are the vault's own
ciphertext, so the point needs no second key and holds no plaintext. Each rewrite is the same
atomic temp-then-move write the rest of the vault uses, so a killed process leaves, per file, the
old bytes or the new bytes, and both open. The next `owner upgrade` resumes: the journal says which
files the point covers, already-current files are skipped, and the lossless re-encoding of every
rewritten file is verified before the journal is marked complete. `owner status` reports
`format=interrupted` while a point is unresolved.

**Status without a credential.** `owner status` shows `format=current`, `format=upgrade_available`,
`format=interrupted` or `format=unknown`, plus `rollback=available` or `rollback=none`, from the
non-sensitive format record (`vault\vault-format.json`: schema versions and counts only) and the
journal. The encrypted inventory stays authoritative; this line only tells the owner whether an
upgrade is worth starting.

**Rollback limits.** A rollback restores *only* the files the upgrade wrote and that still hold
exactly what the upgrade left. A record you changed after the upgrade (a new revision has its own
ciphertext file) and a control state that changed after the upgrade (an unlock moves the epoch) are
kept, not reverted, and are reported as `skipped`. The rollback point is consumed by the first
successful rollback; `owner rollback --discard true` drops it instead, which is how you reclaim its
space. The point is a copy of ciphertext and grows with the number of rewritten files.

**Key and backup compatibility.** The upgrade does not change the passphrase, the recovery key, the
KDF parameters or the key envelope: the header file stays byte-identical, so the same credential
opens the vault before and after. A backup taken *before* the upgrade carries its own copy of that
envelope and the records it captured, so it still restores after the upgrade with the credential it
was taken with. A backup taken after the upgrade restores just the same. There is no reset and no
re-key: losing both the passphrase and the recovery key still means the vault and every backup are
unreadable.

**In the owner console.** The **Backup & export** view carries a *Vault format* card with the same
keyless status line, a passphrase/recovery selector, *Upgrade the vault format*, *Roll back to the
previous format* and the discard choice. The credential goes from the field into exactly one
request and is cleared right after it, and the card's acts are enabled only while the vault is
locked. After an act the card shows the service's own report — the migrated record and control-state
counts, the schema before and after, whether the run resumed an interrupted upgrade, and where the
encrypted rollback point is kept (or that it was restored or discarded); the status line then
re-reads the new format and rollback state.

### 8.1 Partial-source states and troubleshooting (1.1.0 candidate)

When a folder member shows `interpreted=partially_interpreted` (or `uninterpreted`) with a `last_diagnostic {code, offset}`, the source is not broken: the checkpoint stopped at the first complete record the build cannot interpret yet (or the tail is still a partial line). Remediation by exact offset: (a) enable explicit raw preservation (`source-raw-preservation-optin` with a future `--retain-until-utc`, or the folder checkbox for future members) and re-run `source-ingest` so the exact record bytes are preserved and the checkpoint can pass; (b) leave the source reference-only and wait for a newer adapter; or (c) export one exact already-preserved span with `source-preserved-record-read --source-id <id> --offset <byte-offset> --output-file <new-file>` after unlock. Reference-only suffixes stay source-dependent: `unprocessed_bytes` is an honest not-yet-read suffix, not a coverage violation or silent loss, and diagnostics carry only the code and byte offset — never transcript bytes.

An OMP newer-version barrier keeps the checkpoint at the barrier even with preservation on: the entire tail is preserved and owner-readable, but nothing past the barrier is interpreted. A `journal v2` source opened by an older 1.0.0 binary fails closed at the validator (no silent rebuild or partial read); 1.1.0 never downgrades a v2 journal back to v1, even after preservation is turned off. Downgrade note: a reference-only source keeps journal v1 and keeps 1.0 behavior; only a source that already wrote a v2-only element (preserved span or preserved version barrier) requires 1.1.0 to read. Upgrade 1.0 to 1.1 never rewrites existing journals or migrates the vault; fully supported sources keep identical events, spans and digests.

The retention deadline is not a purge trigger. A span whose `retainUntilUtc` has passed is refused read-back by the service with `source_preserved_record_expired`: `owner source-status` and the owner console's Sources view still list that span and its deadline, and the source's availability, preservation, interpretation and derivation facets do not change (the journal revision does not move either). Expiry alone deletes nothing and does not rewrite the journal; deleting a preserved span still requires an explicit owner action such as a purge. `source-raw-preservation-optout` stops future preservation only; it neither shortens the stored retention of an existing span nor removes it, and a new opt-in must name a future UTC deadline (a past one is refused), so an expired deadline is not re-opened by consent alone.

Install/upgrade/coexist/uninstall contract is unchanged from the shared release contract: one complete candidate release upgrades the application files, keeps the selected data root, settings and endpoints, refuses a live shared host or a mismatched shared candidate/version instead of reporting false success, and never deletes the vault, snapshots, backups or recovery material. Host-mutating install, upgrade, coexistence and uninstall proofs remain an explicit owner-executed prerequisite and are not claimed from a repository-local run.

## 9. Diagnostics

The background host writes its operational messages to `<data root>\runtime\service.log`. The log

### 9.1 Operations, audit and error diagnostics (S8-T4)

The owner has one place that answers "what did this vault do, and what failed?": the
**Operations & audit** view of the owner console, and the same four operations on the owner
channel. All four need the unlocked vault and are refused on the agent channel.

```text
owner health      --control-pipe <pipe>
owner audit       --control-pipe <pipe> [--limit N]
owner diagnostics --control-pipe <pipe> [--limit N]
owner retention   --control-pipe <pipe> --retention-days N --max-records N [--purge-log true]
```

- `owner health` reports the vault state, whether the private index is built, whether a provider
  configuration exists, the rolling spend, how many audit entries and diagnostics the private
  operations state holds, the retention that applies, the size of the safe operational log and
  the last recorded error code.
- `owner audit` lists the recorded operations, newest first: the actor (`owner` or `agent`), the
  operation, the outcome (`completed` or `refused`), the real error code, the cost the service
  already charged and the opaque record ID the operation named.
- `owner diagnostics` lists the recorded failures, newest first: the component that failed, the
  **real error code the service returned** and the owner-facing sentence that says what to do
  next. A code the product does not know is still shown, with a generic next action.
- `owner retention` sets how long the private operations state keeps entries and how many it
  keeps, and can clear the safe operational log at the same time. The answer reports exactly how
  many entries were removed. The **whole request is validated first**: a retention choice the
  product refuses (a window outside 1–3650 days, a ceiling outside 10–5000 records) removes
  nothing — not one audit entry, not one diagnostic and not one line of the operational log. The
  private state is written before the log is cleared, so a failed encrypted write leaves the log
  exactly as it was.

What a refusal carries:

- A refused owner operation answers with the **real error code** the product knows
  (`pricing_unknown`, `source_unavailable`, `budget_exceeded`, `token_unknown`, …) and, when it has
  one, the owner's own sentence. The code is what the audit trail and the diagnostics record; the
  sentence stays the owner's answer. A refusal never answers with a sentence in the code position,
  so the trail never has to guess what a free text meant.
- The owner CLI prints the code first and the sentence after it (`ERROR pricing_unknown: …`), and
  adds the product's own guidance line for a refusal that carries only a code.
- The **owner channel client** reads that same contract: the code comes from the typed `errorCode`
  field, the sentence from `error`. A refusal is therefore never reported as an unavailable
  transport, and the owner's sentence is never read as a code. The client keeps both, so the owner
  console shows the real code **and** the service's own sentence of a refused job, schedule or
  recall act (`The service refused this run job (code: pricing_unknown). … The service said: …`),
  and the console log names the act and the code (`owner act: run job -> refused (pricing_unknown)`).
  A refusal that carries only a code keeps the console's own wording and its guidance.

Where the data lives:

- The audit trail and the diagnostics live in **one encrypted file of the vault**,
  `<data root>\vault\operations-audit.enc`, written with the vault's own data key and the same
  AEAD envelope as the scope grants, the catalog, the recall policy, the review state and the
  purge ledger. It is not a canonical record, it is not part of the private index and it is never
  published: the approved catalog stays the only public disclosure of this product.
- The **safe operational log** is `<data root>\logs\operations.log`. It is a plain text file on
  purpose: it holds the operation name, the outcome and the error code and nothing else. Every
  value goes through a sanitizer that replaces anything which is not a short lowercase token with
  `redacted`, so a credential, a token, a path, a title or a payload cannot reach it — not even
  through an operation name a caller invented.
- The audit trail and the diagnostics exist **only while the vault is unlocked**. A refusal that
  happened while the vault was locked has no private entry: the private state lives inside the
  unlocked vault, and the product never keeps a second key, never auto-unlocks and never buffers
  a plaintext queue to write later. Such a refusal is visible in the safe operational log and in
  the console's own answer.

When the trail itself cannot be written:

- The private operations state is written with the vault's own data key. If that write fails (the
  file is damaged, the key or the envelope fails, the disk is full, the vault locked between the
  request and the write), the failure has **one typed form** in the product, so it is never
  mistaken for a refused operation.
- The owner's own act has already happened, so **its answer is never replaced by the failure of
  the trail**. The failure is reported truthfully in the safe operational log as
  `outcome=audit_failed code=audit_persistence_failed`, which is the one trace that survives a
  locked vault. The entry is simply not in the private trail, and the owner can see that.

What the retention choice does and does not do:

- A retention pass removes the entries older than the chosen window and the entries beyond the
  chosen ceiling, and records the removed prefix, so a removed entry does not come back after a
  restart.
- A **purge of a record** also removes the audit entries and the diagnostics that named that
  record, and records their sequence numbers as tombstones. They are not served again by a later
  read, a restart or a restore.
- An **encrypted backup taken before a purge still holds the bytes of that moment**, exactly as
  it still holds the canonical bytes of that moment. A copy is irrevocable: deleting it is the
  owner's own file operation. What a later backup carries is the purge watermark, so a restore
  from a backup taken *after* the purge does not resurrect the removed entries.
- Both halves of that are true at the same time and are proved by the runtime scenario: a restore
  of the **post-purge** backup into a clean vault serves neither the removed audit entry nor the
  removed diagnostic, and a restore of the **pre-purge** backup still serves the entry of its
  moment. The operations state travels with the backup, tombstones included.

#### BOUNDED-A8 — historical first bounded-memory, encrypted-at-rest index (2026-10-22)
**Historical A8 snapshot:** the no-spill wording and measurements below are preserved for the A8 binary, which did not use external scratch files. They do not describe the current A11 builder; see the current subsection below.

The owner-approved correction is implemented: the private index is a **persistent generation file
that is encrypted at rest**, the engine keeps only **bounded structures** in memory, and the recall
path **streams** the candidates instead of materializing them. The frozen targets are not
relaxed; they are measured again against the same numbers.

**What is on disk, and what is not.** The generation lives at `<vault>/private-index/index.v1.bin`
and is a sequence of records, each sealed with the vault's own AES-GCM under a key derived from the
vault data key (HKDF-SHA256, the label `MetaBrain|private-index|v1`). There is no plaintext index,
no plaintext staging file, no journal, no write-ahead log and no temporary file: a staged
generation is ciphertext, and publishing it is one atomic replace. The record's file offset, its
kind, the format version and the **generation identity** are bound into the associated data; the
generation identity is derived from the canonical digest of the set the generation was built from,
so a record of one generation cannot be read as a record of another, and a generation cannot be
replayed as the generation of a canonical set it was not built from. A tampered or truncated generation **fails closed**; a generation that is not the one the
current unlocked epoch materialized is refused as well. The owner rebuilds it explicitly with
`owner index-rebuild`, and the canonical records are never touched. A bounded independent assessment of the file format (whole-generation replay and header
substitution) was run and answered: a header substitution cannot yield a served path; a whole
valid-generation replay is not detected by the engine itself but is refused by the rebuild, by the
owner index status and by both search paths, each of which compares the generation's own canonical
digest with the snapshot's and with the live canonical set. The gap the assessment found — the
rebuild could stamp the live canonical digest onto another generation's rows — is fixed, and the
permanent regression proves it fails without the fix. The assessment is a **diagnosis, not a
security verdict**: no security PASS is claimed here.

**What is resident.** The engine keeps a **directory** (identity, revision and file offset of every
indexed document) with a measured byte budget — a generation whose directory would not fit the
budget is refused instead of being loaded — and a **cache of decrypted records** capped in bytes
(16 MiB by default) and evicted least-recently-used. The postings are never all resident: a query
reads the posting list of the terms it asked for, merges them and scores the candidates in
batches. Locking or restarting drops the key, the cache, the directory and every private read.

**Restart and unlock readiness.** A lock or a process restart does not force a rebuild of an
unchanged generation. The next owner search, scoped search or `owner index-status` in the new
unlocked epoch opens the published generation, authenticates its sealed header and directory with
the borrowed vault key, and loads it only when its authenticated canonical digest and row count
still equal the live canonical resource/revision set. The load is read-only: no staging file is
written and the encrypted generation stays byte-identical. A missing generation still asks for the
explicit `owner index-rebuild`; a generation that describes another canonical set is refused as
`search_index_stale`; a tampered, truncated or wrong-key generation is refused as
`index_unavailable`; and the explicit owner rebuild remains the supported recovery for all three.
A record-level add/revise/delete delta is not applied. The generation is one sealed file whose
directory, token buckets and postings describe the whole vault, and the write scope only appends
rows and merges whole-vault postings at commit, so a changed canonical set goes through the
existing explicit rebuild instead of an unversioned merge.

## 10. Verifying the installed lifecycle

The repository's permanent smoke drives the real installer and the real installed host end to end:

```text
dotnet run --project tests/MetaBrain.S1T4.Smoke/MetaBrain.S1T4.Smoke.csproj -- s8-t1 <published-payload-dir> <fixture-root>
```

It installs into a fixture inside the repository, starts the host, proves it is locked, provisions
and unlocks the vault, stores and reads an owner record, issues a grant, redeems it, uses a live
agent session, stops, restarts (locked again, session gone), uninstalls and proves the vault
survived. It also fingerprints the product paths it watches — the settings file, the vault
directory and the files inside it, the runtime log, the grant handoff and the session
handoff: each path must still exist with the same bytes after the stop, restart and
uninstall phase, so the run fails if the lifecycle deleted, replaced, or truncated one of
them. Ordinary permissions are neither inspected nor changed by the product or the run. The fixture
root has to live inside the repository: the smoke refuses a fixture outside it, and it
removes the fixture when the run ends.

## 11. Known limits

- A real logout or reboot, and a connection from the official Codex/OMP clients,
  need the owner in front of the machine; they cannot be proved by a headless run.
- The installer is Windows-only and per-user. There is no multi-account or shared-machine install.
- The vault is lost if the owner loses both the passphrase and the recovery key. There is no reset
  and no back door.
- The same owner account can read the owner's own files. The boundary is the key, the lock and the
  owner-approved APIs, not the access rights of the file system: malware running as that account is
  not stopped by file permissions.
- The legacy cutover (`owner migrate`, §1) removes the plaintext copies it migrated once the
  encrypted vault and the settings file are committed. It changes no permission and no ownership,
  and the service must be stopped. A cutover interrupted between the vault creation and the
  settings write is resumed only when the passphrase opens the new vault and every legacy record is
  byte-identical; otherwise it refuses untouched.
- The format upgrade (§4.2) runs only while the vault is locked and the service is running. Its
  rollback point is a ciphertext copy of the rewritten files, restores only files unchanged since
  the upgrade, and is consumed by the first rollback. The upgrade does not re-key the vault, so old
  backups keep restoring with the credential they were taken with.
- The operations view (§9.1) is local. This build has **no telemetry, no auto-update and no cloud
  reporting**. Separately, an owner-started model job or an explicitly enabled provider-backed
  schedule can make an outbound request to the owner-configured provider; this is provider egress,
  not telemetry. Selected inputs may be disclosed to that provider, and content already sent
  cannot be recalled. S8-T6 did not exercise actual provider egress or model-level injection without
  separate owner consent; approval-preview non-disclosure was verified, not the model/provider
  boundary.
- S8-T6 passed independent evidence review and exact-snapshot checkpoint
  (R4,
  C1). Nonblocking limits are actual provider
  egress/model-level injection not exercised and strict simultaneous redemption overlap not
  attested (one consumption across two clients was observed); owner aggregate runtime reports were
  accepted without redundant raw bundles.
- S8-T7 release-level owner approval remains pending. The accepted T5-specific qualitative
  judgement is not a substitute for the separate release decision; see the
  T7 task record.
- The audit trail and the diagnostics are private to the owner channel. An agent never receives
  them, and there is no operation that enumerates stored credentials: the health view says
  whether a provider configuration exists, never what it holds.
- The safe operational log is plain text by design, so it can be read without unlocking the
  vault. It carries operation names and error codes only; the sanitizer is what keeps a secret
  out of it, and a sanitized value that is not a plain token is written as `redacted`.
- The same owner account can read the owner's own files, including the safe operational log and
  the encrypted operations file. The boundary is the key, the lock and the owner-approved APIs,
  not the access rights of the file system.
